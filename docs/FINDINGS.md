## Capture schedule re-test

**A redesigned capture schedule fits the plugin's per-tick budget headless, with a thin margin, and in
the project owner's real play, so the re-test passes. The design's own per-unit safety check fails because of one-off
stalls the allowance cannot bound.** Three valid, complete 35-day runs of the full workload measured a worst
tick of 9.469 ms and 0.3165 ms per tick on average, against limits of 10 ms and 1.25 ms (worst of the 3;
observational, one machine and one park copy). Real play, in the project owner's usual window, renderer and plugins,
measured 4.483 ms and 0.1491 ms per tick over 47 game days and felt smooth to the player (one player, one session,
observational).

- **What the pass means.** All capture work sits in one queue, and each tick runs queued units (one guest,
  one ride, one send) until a 4 ms allowance is used. Guests are tracked by ID and checked once per game day,
  so the 2026-09-28 design's whole-park reads are gone. The headless runs leave out the game's window,
  renderer and other plugins; the real-play session includes them.
- **The margin is thin, and the stalls explain why.** The worst tick had 0.53 ms of headroom. It contains one
  6.992 ms call in a guest-check step that normally takes 0.008 ms, and the design's own per-unit safety
  check fails in all 3 runs. These one-off stalls fit garbage-collection pauses in the plugin's JavaScript
  engine (QuickJS-ng in 0.5.5; unconfirmed: the probe looked for `Duktape.gc()` and could not force a
  collection), which the per-tick allowance cannot bound. None pushed a tick
  past 10 ms in 3 × 35 game days. The largest stall measured, though, was one 9.655 ms `send` call in the
  2 ms screening run, which alone took that tick to 10.504 ms: the only over-10 ms tick in any
  queue-schedule run (about 165 game days at normal speed; none in 105 more at speed 8). The same stall
  after a full 4 ms allowance would give a tick of about 13.7 ms. The `day_start` unit also shows recurring
  multi-millisecond calls at each day's start (run 3: 5.664, 4.655 and 3.159 ms; run 2: 3.630 and 3.436 ms;
  it was the worst tick of run 3 and of replay runs 1 and 2), which is the basis for the recommendation
  for the full-capture spec: find and reduce the allocation behind the stalls (for example, reuse task
  objects instead of allocating about 2,000 a game day at the day's start) and re-measure, keeping the allowance at or below 4 ms. That gains margin under
  the limit; it costs a change to the queue's task handling and another measurement round.
- **The extra slow tick is located.** It came from the old trial schedule's daily snapshot and its sends
  piling into the first two ticks of each game day (19 ticks over 10 ms, worst 19.962 ms). The queue schedule
  had no tick over 10 ms in any verdict or replay run; the one over-10 ms tick in a queue-schedule run is the screening-run stall above.
  The overnight trials that led to the re-test (kept in the project folder's notes, not in this record) had the
  same shape: worst ticks of 21 to 23 ms and 66 to 68 ticks over 10 ms per 35 game days, from the snapshot's
  first slice (10 to 13 ms, reading the ride and guest lists before building anything) plus its sends (7 to
  8 ms).
- **The daily guest check costs about as much as one whole-park scan, spread thin.** The check calls
  `map.getEntity(id)` once per known guest per game day: about 1,960 calls at 0.010 to 0.011 ms, roughly 20
  ms a day (derived from the unit-cost row). One whole-park scan pass measured 24.87 ms. The check needs no
  call that reads every guest at once, which is what removed the scan's single-tick cost. It gives exits and
  price complaints at day resolution only; the project owner accepted that on 2026-09-29.
- **Sending previews fits.** On the busiest recorded minute (8,576 previews) injected into running ticks, the
  worst tick in the window was at most 6.011 ms, every run drained and dropped nothing. The drop-or-label
  decision (ADR 0006) belongs to the full-capture spec. The pass rule was fixed before any run: in all 3
  runs, worst tick in the window at most 10 ms, mean over the window at most 1.25 ms, the queue drained
  within the game day, and no line dropped. The window holds 143 previews a second (up to 131 in one 25 ms

  drained. Across the 2026-09-26 and 2026-09-27 captures, 216,921 of 219,413 recorded `game_action` events
  are previews or client-side predictions. The replay adds 2 to 3 MB of script data, which enlarges the
  heap, so replay runs are compared only with their own ticks outside the window, never with the full
  workload runs. The replay times the send only: the cost of subscribing to `action.query` and
  `action.execute` to see previews has not been measured, so the full-capture spec must measure it.
- **Speed 8.** The workload makes a game day 23% longer than the idle plugin at speed 8 (0.172 against 0.140
  s), against +179% for the failed workload.
- **Deviations and limits.** The park-guest count check allows the period's arrivals as slack. In real play
  each session's last partial game day is never judged. The harness's autosave guard cannot see a game left
  paused, so runs also waited for a 1-minute load average under 3.0. The probe's files (1,384 and 1,151
  lines) exceed the 500-line aim and are split when the probe becomes the repo benchmark. The v1 core workload (the smaller fallback) was not run, because the full workload passed headless.
- **Method, so later checks compare directly.** The clock is `performance.now()`. Each hook callback is one
  timed span, added to a bucket per tick. The average is total probe time over every tick in the window,
  including ticks with no callback (0 ms). The partial game day the probe starts in is warm-up: startup work
  and the socket connect are reported, never judged. A run is valid when it reached its target days, `seq` has
  no gaps or duplicates, there are no `probe_error` events, the fixture SHA-1 matches, and the boarding polls
  and finance reads ran as often as scheduled. It is complete when each game day's queue drained within the
  day, no line was dropped, and each day built its 200 sampled guest records (or every live guest if fewer)
  with an end-of-run guest count within 2% of the probe's known set. A verdict needs 3 valid, complete runs
  and takes the worst of them. Runs are one at a time, and the harness refuses to start within 10 minutes of
  a real autosave in the project owner's folder, so the game is not running alongside.
- **Real-play method, for any later real-play check.** The game is launched from Applications with the project owner's own
  settings, not a fresh config. The figures pool every session on the benchmark park, because a reload
  starts a new session: the worst tick is the maximum over sessions, the mean is total time over total
  qualifying ticks, each session's warm-up is excluded, and only ticks at normal speed count. At least
  24,000 qualifying ticks (10 minutes unpaused) are needed, and fewer is "too short, not judged". The player's
  "smooth or stutter" answer is recorded but does not decide the verdict. The probe does nothing outside
  normal mode or off the benchmark park, so a copy left in the plugin folder is idle. The game's autosave keeps
  10 files and a 15-minute session makes about 3, so the autosave folder is backed up first.

## Save hook (`map.save`)

**In OpenRCT2 0.5.5, a value the plugin writes to park storage inside the `map.save` hook reaches the saved
file for plugin-triggered saves, the game's autosaves (headless and windowed) and saves from the game's Save Game

copies of one park and one player for the menu saves (observational). Plain Save Game, which saves without a
dialog, and the save offered when quitting were not tested.

- **What the pass means.** Two plugin saves and the newest autosave were each loaded in a separate run, and
  the plugin read back the save ID, session, `seq` and hook count that the hook had written. The reloaded
  copies' SHA-1s equal the saved files'. It does not say when the file's bytes were written, only that the
  hook's writes are in them. The game's own log records nothing about any save, so the probe's events are
  the only record of when each save happened.
- **The pending-ID fallback is not needed.** The probe also set a pre-set ("pending") save ID ahead of time, in
  case the hook's writes missed the file. The reloads carried the ID the hook newly minted, as expected when
  the hook's writes reach the file, so the fallback was not what got saved.
- **The hook fires inside `saveGame`.** For both plugin saves, `save_call`, `save_hook` and `save_returned`
  all landed on the same game tick, in that order.
- **Autosave timing.** The first autosave landed 60.01 s after start and the next 59.94 s later (about 0.80
  autosaves per minute). The hook-to-file gaps were 0.133 s and 0.001 s, and each hook matched exactly one file
  within 5 seconds.
- **One run was voided.** An earlier autosave run was discarded because a park was saved
  in the real save folder during it, which tripped the probe's real-save guard (the check that the real save folder
  is unchanged). The project owner confirmed this, and the run was repeated once; its folder is kept unchanged and not
  used.
- **Menu saves reach the file (2026-10-01).** Headless runs cannot use the game's menu, so the project owner
  played the windowed game (the script `run_windowed.py` in the project folder's notes) and saved twice through
  Save Game As. Each menu file, read back in its own headless run, held the ID its hook had written 0.023 s and
  0.026 s before the file appeared, and the newest autosave of the same session held its hook's ID too. This
  closes the roadmap's "Save-hook test" slice.
- **Two windowed attempts were void.** The Save As dialog first opens in the folder the park was loaded from,
  one level above the folder the script watches, so the first menu saves of both attempts landed where the
  checker could not pair them with their hooks: the first attempt was invalid and the second inconclusive. The
  script was then changed (its steps name the folder, it announces each file as it lands, and autosave moved
  from every minute to every 5 minutes, so no menu save can land within the checker's 5-second pairing window of

- **Conditions.** OpenRCT2 0.5.5, headless, in isolated user-data folders under the scratch directory; copies

## Price variation spike: rules, engine facts and per-type counts

**The 2026-10-10 price variation row above is inconclusive and provisional: the value check failed, so no ride type
is judged, and the project owner's window check is still open.** This section keeps what the row cites: the pass
rules fixed on 2026-10-03 before any save was read, the game facts the rules rest on, the window check, and the
counts per ride type. The probe code and its evidence are in a git-ignored folder and are not committed.

### Rules fixed before the run

Prices and values are read as the plugin API returns them. The ratio r of a ride is its first price divided by its
`value`; both sit on one scale inside the engine (see the engine facts below). Verdict order: inconclusive when fewer
than 20 saves read validly (S1); inconclusive when the value check V fails; pass when at least 3 types pass;
inconclusive when at least 3 types pass or are inconclusive (a type is inconclusive when it meets R1 to R3 only with
its V-disagreeing rides added back); fail otherwise. Every verdict is an inventory and states `model_ready: not
established`, because a save cannot show how many customers came at the saved price.

- **Q-park:** a park qualifies when `no_money` is false and `free_park_entry` is true (pay-per-ride, the company's own
  model). The ignore-price flag is reported per type, not used as a filter, and is unverified.
  Notes for NEXT 8 (the v1 pricing model): it must exclude parks whose flag reads true, because guests ignoring price
  would mislead its demand figures; and it should test its slope with more flexible ratings terms, because a ratio
  that is a curved function of ratings would leave misses that the planned linear adjustment also uses.
- **Q-ride:** the park qualifies, the ride is classed `ride`, its excitement is 0 or more, it has a price, and its
  `value` is above 0 and not the observed undefined value.
- **Q-use:** the ride is open, its first price is above 0, it is at least 1 month old, has at least 1 customer and an
  income per hour above 0; a ride whose price changed between saves needs a new customer since the first save at the
  kept price.
- **Spread park for a type:** a lineage (one park followed across its saves) with at least 4 usable rides of the type
  where both the ratio r and the relative price (price divided by the type's median) have a trimmed span (second
  largest minus second smallest) of at least 0.30.
- **R1:** at least 30 usable, V-agreeing rides of one type; the 90th minus the 10th percentile of r at least 0.50; at
  least 3 distinct first prices. **R2:** those rides come from at least 5 lineages. **R3:** at least 20 of them sit in
  spread parks, from at least 4 spread parks; and after fitting r on one intercept per spread park plus excitement,
  intensity, nausea and age, at least 10 rides miss by 0.10 or more, from at least 3 spread parks.
- **V (value check):** at least 90% of usable rides have a `value` within 1 of the value recomputed from the ride's
  ratings with the v0.5.5 formula, at the ride's age or one month younger. **S1:** at least 20 valid saves. **B (build
  dates):** among at least 10 ride identities new between consecutive saves of a lineage, each build date lies between
  the two saves' `months_elapsed`; if B fails, a fallback lineage rule (same ride ID and type, whatever the build date)
  applies, which errs toward fail.
- **Why 0.50:** the engine treats a price at or under half the value as good value and refuses a ride above twice its
  value, so 0.50 is a third of that band. All thresholds are pre-run heuristics, not proven floors for estimating a
  price slope.

### Engine and API facts the rules rest on

- **Verified in the OpenRCT2 v0.5.5 source** (`Guest.cpp`, `Ride.h`): guests compare a ride's price with its value
  directly. A guest refuses a ride priced above twice its value (the "bad value" thought), except with a voucher for
  that ride or with the ignore-price cheat on; thinks a price at or under half the value is good value; and, having
  paid to enter the park, quarters the value first. An undefined value sets no limit.
- **Value calculation** (`RideRatingsCalculateValue`, `RideRatings.cpp`, v0.5.5): the value falls with the ride's age
  and with the number of open rides of the same type (a duplicate penalty), so price divided by value varies even when
  prices never change. With `cheats.disableRideValueAging` the age is taken as 0, which adds 30; it does not stop
  aging, and there is no 1.5 multiplier.
- **Not exposed by the 0.5.5 plugin API:** no field records when a ride's price last changed (so lifetime customers can
  belong to earlier prices), and no value exists for a shop item (shop prices are described, not judged). Ride
  `price` is an array: the ride's admission price and the on-ride photo price, or the cost of each stall item.
- **Recalled, not verified, and not relied on by any rule:** in a park that charges entry, ride prices are locked at 0
  unless `unlockAllPrices` is set; `cheats.ignoreRidePrice` is stored in the save; the value is in tenths of a dollar;
  the number the API returns for an undefined value was to be observed in the dry run (the earlier assumption of
  65,535 was dropped).
- **Build dates** are on the `months_elapsed` clock, so scenario rides built before play carry a build date at or
  below 0. The judged run showed the build-date check failing (212 of 689 identities outside), so this is not a safe
  assumption for linking saves.

## One-script install: draft and static check

**A fresh Mac needs Apple's Command Line Tools, three downloads (uv, Node, direnv) and the game; a draft script covers the three downloads without Homebrew, and nothing has been run on a real machine yet.** The checks so far are a syntax check of the script, one dry run of it, a read of the Makefile and launcher, and three `make -n` dry runs with direnv off the PATH (2026-11-16). The project owner's steps are below: copy the folder, run the dry run, then the real run in a new account.

- **What a fresh install needs.** Apple's Command Line Tools (git and make; macOS shows an installer window), uv (it fetches the pinned Python 3.12 itself), Node 24 (the version CI uses; `npm` ships with it), direnv (the launcher refuses to start without it), the OpenRCT2 0.5.6 app, and the player's own RollerCoaster Tycoon 2 files, which `config.ini` names as `game_path`. The six commands the roadmap item names for the before-and-after record are git, make, uv, node, npm and direnv.
- **What the draft script does.** It lives in `~/Library/Application Support/mac-tools/openrct2-setup/` in the project owner's account and is not in this repo. It downloads uv (a pinned release archive, checked against the SHA-256 file the release publishes), Node (the nodejs.org tarball, checked against its SHA-256 list, unpacked in a new folder and put in place only when that worked, and only over a folder the script made earlier) and direnv (a pinned release file, moved into place only after the download finished). All go under `~/.local`, with no Homebrew and no sudo, and nothing is piped into a shell. It appends one PATH line to `~/.zprofile` (the launcher runs a login shell), runs `git init` when the folder is not a repository (`make setup` refuses otherwise), then `make setup`, `direnv allow` and `make launcher`. It never copies game files and ends by printing what is left for the player.
- **Not verified.** direnv is not checked against a checksum, because its releases publish none; it is pinned to one version only. The uv version in the script is a placeholder, and the exact uv asset names (`uv-<cpu>-apple-darwin.tar.gz` with a `.sha256` file beside it) need checking on the first real run; the script refuses to download uv until a version is set.
- **Re-running.** Tools already present are skipped. An existing launcher app in `~/Applications` is kept, because `make launcher` deletes and rebuilds it; `--rebuild-app` rebuilds it on purpose. A `~/.local/node` folder the script did not make is refused, not replaced.
- **Launcher and direnv.** The launcher calls `make dashboard`, `make auto-file` (twice: `RECORD=yes` before the play and `COUNT_AS=...` after it) and `make play`. Run: in the worker copy with direnv off the PATH (uv, node and npm kept), `make -n auto-file DATA_SET=company RECORD=yes`, `make -n play DATA_SET=company` and `make -n dashboard DATA_SET=company` each print one command that picks `uv run` or `.venv/bin/` on its own, with no direnv step; `make -n` prints the same commands with or without uv on PATH, because the Makefile chooses between `uv run` and `.venv/bin/` only when the recipe runs; the `.venv/bin/` fallback was read in the Makefile, not run. Dry runs print commands only, so they show the choice and not that the tools work. Read, not run: `make play` builds the plugin with `npm run --silent plugin:build` (`src/openrct2_analytics/ingest/plugin_install.py`), so npm and node must be on the PATH. The launcher script itself does need direnv: it stops when `direnv` is missing or the folder is not allowed, and it runs every step as `direnv exec . make ...`. So direnv stays a required tool until the launcher changes.
- **Checked.** `bash -n` on the script: pass. One `--dry-run` of the script on the owner's account: it only printed and read tool versions. `shellcheck` was not installed, so it did not run.
- **Not measured.** A real run in a new standard macOS account; what macOS shows when a downloaded archive or the built app is opened; whether the direnv release file runs unsigned; whether the commands typed fall to 1; whether `config.ini` names `game_path` on a new account.
