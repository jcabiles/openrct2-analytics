# dbt practices for the park company's warehouse — research findings

status: complete; adopted in ADRs 0019 and 0020 (provisional); the project owner's rulings are recorded in section 19 · date: 2026-10-06 (rulings 2026-10-06; lane 10 folded in 2026-10-07) · initiative: park-company (roadmap NEXT 3·0, "dbt design and setup", and NEXT 3a, the staging slice) · feeds: ADR 0019 (`docs/adr/0019-dbt-practices.md`), which supersedes parts of `docs/adr/0016-dbt-design.md`, and ADR 0020 (agent working rules, decision 12), the dbt rules in `docs/CONVENTIONS.md` and `.claude/rules/dbt.md`, and new roadmap items

## Bottom line

- **The current dbt design holds up.** Twelve research lanes agree with almost every choice in ADR 0016 (the dbt design record): the star schema with wide tables built from it, full rebuilds, no snapshots, year-over-year computed in SQL. Where the repo departs from dbt's defaults, the new ADR should say so and give the reason.
- **No finding reverses a ruling made for the NEXT 3a staging slice.** The research adds small items to it: argument docs for the money macro, stored rows for the duplicate warning, unit-and-clock descriptions, no `unique` test on the raw `event_id`, and "first-received" meaning the order of `received_at` (when the listener received the event), never `emitted_at` (when the game sent it).
- **The newer lanes add cheap safeguards, not new architecture:** marking day-start balances (cash, guests in park) as unsafe to sum, a guard on joining two fact tables, day counts beside every year-over-year number, and event-data checks for sessions and counter resets after a reload.
- **Still no dbt packages.** dbt-project-evaluator (dbt Labs' project linter) is now backed by two lanes and remains the one package worth a probe.
- **Being AI-first here means three local things:** a short list of agent-safe commands enforced by gate checks, a deterministic test suite for the coding agents, and governed metrics later. Hosted dbt agents and AI-graded CI gates are not adoptable or not trustworthy yet.
- **Corrections:** dbt Fusion (dbt's newer engine) is now generally available as dbt v2, not "in preview"; it is still not adopted. One lane's recommendation contradicts a standing ruling (company-wide year-over-year) and is not adopted. Lane 10 (DuckDB, lakehouse formats, portability, contracts) is folded in: keep one DuckDB file per environment, describe the stack as "DuckDB-first" (never "portable"), and gate contract changes with `datacontract breaking`.
- **The project owner has ruled on every decision.** All 19 were accepted as recommended (option A); section 19 lists them, the adopted and rejected items, and the seven roadmap items.

## 1. Staging and sources (the NEXT 3a slice)

**In plain terms.** Staging is the first cleaning step: one table per kind of game event, with columns renamed, typed, money converted once and placeholder numbers blanked. dbt's guidance agrees with that job description, and the event-data packages that analytics teams use (Snowplow, GA4) all remove duplicate events in their first layer, as the repo does. Three of the repo's staging choices differ from dbt's defaults (tables instead of views, singular names without a source prefix, contracts on staging); each has a reason and should be written down. Two rules matter for NEXT 3a: a uniqueness test belongs after staging removes repeats, not on the raw source; and "keep the first-received copy" must order by the listener's receipt time, not the game's send time.

**Technical detail**

- **Practice:** staging is one model per source table, the only place `source()` appears; allowed work is rename, cast, simple arithmetic and bucketing; no joins or aggregations; materialize as views. https://docs.getdbt.com/best-practices/how-we-structure/2-staging (as of 2026-10; strong). **Pitfall:** treating "views" as mandatory. ADR 0013 bars views from published files, and each build starts from an empty DuckDB file, so tables cost little; the docs give a default and an upgrade path, not a prohibition (lanes 1 and 8). Record the departure.
- **Practice:** name staging `stg_<source>__<entity>s` (same page; strong). **Pitfall:** the source segment only pays off with several source systems; this repo has one (the plugin), and the event name, contract name and model name already match. Keep `stg_<event_type>`; rename if a second source system appears (lane 1). dbt-ga4 also builds one staging model per event type (`stg_ga4__page_view`, `stg_ga4__purchase`) from one cleaned event model, so per-type staging has precedent. https://github.com/Velir/dbt-ga4 (as of 2026-10; moderate; lane 8).
- **Practice:** a macro is worth writing for a transformation applied identically everywhere; dbt's own example is `cents_to_dollars`, pushed into staging. https://docs.getdbt.com/best-practices/how-we-structure/2-staging and https://docs.getdbt.com/docs/build/jinja-macros (as of 2026-10; strong). Document macro arguments in a properties file; from dbt 1.10 the `validate_macro_args` flag checks documented arguments against the definition (same jinja-macros page; strong for the docs, **not run on 1.11.15**). **Pitfall:** "favor readability … even if it means repeating some lines of SQL" (same page). Keep one money macro. dbt 1.11's new function resources (UDFs) do not replace it: DuckDB is not on their adapter list, and a compile-time macro already enforces the single conversion (section 13).
- **Practice:** deduplicate in staging with `row_number()` over `event_id`, keep rank 1; Snowplow's base layer deduplicates before anything else is built. https://docs.snowplow.io/docs/modeling-your-data/modeling-your-data-with-dbt/package-mechanics/incremental-processing/ (as of 2026-10; strong for Snowplow); the `row_number` pattern itself rests on blog-tier sources (weak; lane 8). **Pitfall:** ordering by `emitted_at` makes "first" depend on the game's clock; order by `received_at` (the envelope contract carries it, `contracts/envelope.odcs.yaml`), then by file and line order (lane 8, inference; the field's presence is a repo check). This sharpens the ruling; it does not change it.
- **Practice:** staging cleans or flags business anomalies at the boundary; sentinels to null fits this. https://docs.getdbt.com/blog/test-smarter-where-tests-should-go (as of 2026-10; moderate, a dbt Labs blog). **Pitfall:** testing every staging cast duplicates the implementation and adds noise (same source; lane 2).
- **Practice:** declare sources in YAML; dbt-duckdb reads Parquet through an `external_location` setting. The repo's `models/staging/_sources.yml` already sets `config.external_location` per table and builds in the gate (repo run, strong). **Pitfall:** lane 1 cites `meta.external_location` from a tier-3 summary (https://motherduck.com/docs/integrations/dbt, as of 2026-10); the repo's working `config` key outranks it (section 17).
- **Practice:** datacontract-cli (already a dependency) exports `dbt-sources` (`datacontract export dbt-sources <contract>`), `dbt-models` and `dbt-staging-sql` from ODCS contracts. https://cli.datacontract.com/ (as of 2026-10; moderate). **Pitfall:** what each exporter emits was not on the page fetched (gap). The ruled source generation should start with a probe of `dbt-sources` output.
- **Practice:** select named columns in staging, never `select *` from a source, and state in each staging model's YAML which contract version it accepts, so a new contract version fails a test instead of drifting in silently (lane 8; weak, inference from the repo's versioned-contract rule). **Pitfall:** a wide payload column carried past staging pushes type parsing into every consumer (same lane, inference).
- **Practice:** put `unique` and `not_null` on the primary key of every model. https://docs.getdbt.com/best-practices/how-we-style/5-how-we-style-our-yaml and https://docs.getdbt.com/docs/build/data-tests (as of 2026-10; strong). This confirms the ruled gate script. **Pitfall (reconciler's inference from ADR 0006, weak):** the contract states events may repeat, so a `unique` test on the raw `event_id` would fail by design. Put `not_null` on envelope fields at the source and `unique` on `event_id` only in staging, after the dedupe.
- **Practice:** a warning needs an owner and a review path; `store_failures` keeps the failing rows. https://docs.getdbt.com/reference/resource-configs/severity and https://docs.getdbt.com/reference/resource-configs/store_failures (as of 2026-10; strong). Lane 8 suggests the test itself: count distinct payload hashes per `event_id` (inference). **Pitfall:** warnings nobody reviews cause alert fatigue (test-smarter blog above; moderate).
- **Practice:** enforced contracts work on tables, views and incrementals, belong on marts and public models, and need explicit numeric scale. https://docs.getdbt.com/reference/resource-configs/contract (as of 2026-10; strong). ADR 0016's probe showed a contract catches a wrong decimal scale even on an empty table (repo run, strong). Record the money-carrying staging contracts as a deliberate extension.
- **Gap, partly closed:** dbt's staging page lists rename, cast, arithmetic and bucketing; a `row_number()` filter is none of these. Lane 8 shows the reference event packages dedupe in their first layer (strong for Snowplow), which supports the ruling; no dbt Labs page addresses it directly.
- **Practice (lane 10, contracts end to end):** an ODCS contract (the open data-contract standard) states what a producer promises (schema, meaning, quality); a dbt model contract states the shape of a model's output. They cover different boundaries. https://bitol-io.github.io/open-data-contract-standard/v3.2.0/home/ and https://docs.getdbt.com/docs/mesh/govern/model-contracts (as of 2026-10; strong). Make the ODCS contract authoritative for each incoming event type and check it against landed local files; the Data Contract CLI tests local Parquet, JSON and CSV, and its dbt integration syncs contract schemas and tests into model properties, runs them, or exports dbt source and model YAML and staging SQL (`export dbt-sources` produces the source YAML) (needs dbt 1.10 or later). https://docs.datacontract.com/testing/local and https://docs.datacontract.com/dbt (as of 2026-10; strong). dbt contracts apply to models, not sources, so staging is the boundary for source data (https://docs.getdbt.com/best-practices/how-we-mesh/mesh-5-faqs, as of 2026-10). **Pitfall:** never hand-maintain one raw-event schema in both ODCS and dbt YAML: `datacontract dbt sync` tags what it generates and preserves unrelated content by default, but `--prune` removes contract-managed content absent from the contract; keep hand-written mart contracts apart from generated content; declared constraints are not enforced alike everywhere (Snowflake does not enforce unique, primary-key or foreign-key), so keep dbt tests where uniqueness matters.
- **Practice (lane 10, versioning):** ODCS `apiVersion` names the standard's version; the contract's own `version` tracks the document. Use contract versions for producer schema changes and `datacontract breaking` to classify them (https://docs.datacontract.com/compare-contract-versions, https://bitol-io.github.io/open-data-contract-standard/v3.2.0/fundamentals/, as of 2026-10; moderate); use dbt model versions only when a shared mart changes incompatibly and consumers need a migration window (https://docs.getdbt.com/docs/mesh/govern/model-versions, as of 2026-10; strong). **Pitfall:** dbt itself advises against adding governance structure too early.

## 2. Structure, naming, materialization and schemas

**In plain terms.** dbt's three layers (staging, intermediate, marts) are what the repo already has. dbt Labs defaults to views and throwaway steps because those cost nothing in a cloud warehouse; on a small local file rebuilt every time, tables are the better trade, and the docs allow it. The `fct_`/`dim_` names are a Kimball (star-schema) convention, not dbt Labs' own naming; keeping them is fine if the ADR says so.

**Technical detail**

- **Practice:** intermediate models are ephemeral by default, "views in a custom schema" when debugging matters. https://docs.getdbt.com/best-practices/how-we-structure/3-intermediate (as of 2026-10; strong). **Pitfall:** ephemeral models cannot be queried or contracted (same page). ADR 0016's tables are consistent with the docs' own upgrade path.
- **Practice:** marts are entity-grained and wide; avoid joining more than 4–5 concepts in one mart; subfolders by business area past about ten marts. https://docs.getdbt.com/best-practices/how-we-structure/4-marts (as of 2026-10; strong). **Pitfall:** the official pages name marts by plain entity; `fct_`/`dim_` appears only in dbt's Kimball tutorial and third-party pages (lanes 1 and 7). Say in the ADR that the star convention is chosen.
- **Practice:** golden rule: views first, tables when queries are slow, incremental when builds are slow. https://docs.getdbt.com/best-practices/materializations/5-best-practices (as of 2026-10; strong). Snowplow reprocesses every event of any session that received a new event, so partial sessions never produce inconsistent results; a full rebuild gives that for free (https://docs.snowplow.io/docs/modeling-your-data/modeling-your-data-with-dbt/package-mechanics/incremental-processing/, as of 2026-10; strong for Snowplow, lane 8). **Pitfall:** incremental logic can miss late records and leave old outputs stale after a logic change (https://docs.getdbt.com/docs/build/incremental-models, as of 2026-10; strong; lane 3). Keep ADR 0016's 5-minute revisit threshold; if it is crossed, compare incremental output with a full rebuild, including late data, before switching (lane 3, inference).
- **Practice:** overriding `generate_schema_name` is supported; dbt warns to keep `target.schema` in the result so developers do not overwrite each other. https://docs.getdbt.com/docs/build/custom-schemas (as of 2026-10; strong). **Pitfall:** the repo's bare layer schemas drop that protection; it is safe only because each environment is its own DuckDB file (ADR 0013). Write that reason beside the macro.
- **Practice:** seeds hold small, version-controlled reference data with `column_types` set. https://docs.getdbt.com/docs/build/seeds (as of 2026-10; strong). **Pitfall:** seeds without descriptions or types hide their meaning.
- **Style guide gaps** (https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models, as of 2026-10; strong): the guide pluralizes model names, keeps keys as strings, and orders columns ids, strings, numerics, booleans, dates, timestamps. The repo's names are singular, game keys may be integers, and staging lists envelope fields first. The guide calls itself a suggestion (https://docs.getdbt.com/best-practices/how-we-style/0-how-we-style-our-dbt-projects, as of 2025-04); state the departures in `docs/CONVENTIONS.md`.

## 3. Dimensional modeling

**In plain terms.** The star schema (fact tables of events or daily readings, joined to dimension tables of parks, rides and dates) is still what dbt Labs teaches and what its metric engine is built to sit on. The repo's design matches it. The real risks are three classic mistakes, not the star itself: adding up day-start balances (cash, guests in park) across days, joining two fact tables directly and summing, and declaring a grain without a uniqueness test. The repo already guards the third; the first two need a note and a test each. dbt's snapshot feature is the wrong tool here.

**Technical detail** (lane 7 unless stated)

- **Practice:** four-step design (business process, grain, dimensions, facts); the star as the mart shape; a wide "one big table" built from the star, not instead of it. https://docs.getdbt.com/blog/kimball-dimensional-model (as of 2026-10; strong). The semantic layer works over stars, wide tables or Data Vault, and "it's best to allow MetricFlow to handle some level of denormalization". https://docs.getdbt.com/docs/use-dbt-semantic-layer/sl-faqs (as of 2026-10; strong). **Pitfall:** dbt's marts page (pack concepts into wide entity tables) and the FAQ pull in different directions; the repo's star-plus-derived-wide pattern satisfies both.
- **Practice:** four fact types: transaction, periodic snapshot (one row per period, even with no activity), accumulating snapshot (one row per process instance, several date keys, updated as milestones pass), factless. https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/periodic-snapshot-fact-table/ and .../accumulating-snapshot-fact-table/ (as of 2026-10; strong). In this repo `fct_park_day`, `fct_ride_day` and `fct_park_month` are periodic snapshots, `fct_ride_boarding` a transaction fact; a guest visit (arrival to exit) would be an accumulating snapshot. **Pitfall:** day-start balances such as `cash_usd` and `guests_in_park` are semi-additive (they add across parks, not across days); summing over days is wrong. The design already stores rating as a sum plus a day count.
- **Practice:** conformed dimensions are shared across facts; a bus matrix (business processes against shared dimensions) shows which attach where. Kimball techniques page (as of 2026-10; moderate). The repo already has one in `docs/requirements-brief.md` (roadmap NEXT 13c); the gain left is showing it on the docs site. **Pitfall:** a density gap: a closed ride with a missing day would silently shorten a denominator; `fct_ride_day`'s `is_open_day` keeps density.
- **Practice:** MetricFlow restricts fan-out and chasm joins, joins fact to dimension with left joins and across facts with full outer joins; joins reach at most three tables and two hops. https://docs.getdbt.com/docs/build/join-logic (as of 2026-10; strong). The same discipline in plain SQL: aggregate each fact to a shared grain, then join. **Pitfall:** `fct_ride_day` links to `fct_park_day` through `park_day_key`; that join is safe for reading park attributes (weather) onto ride rows, never for summing park-day measures. A singular test can guard it (inference).
- **Practice:** a type 2 slowly changing dimension adds a row per change with effective dates. https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-2/ (as of 2026-10; strong). Fast-changing attributes (price, rating, status) belong on a periodic-snapshot fact, which the repo already does on `fct_ride_day` (Kimball type 4 rationale; moderate). **Pitfall:** dbt snapshots "can't be rebuilt" and ignore `--full-refresh`. Change timing depends on the strategy: the timestamp strategy uses a source `updated_at` column, while the check strategy records the time dbt ran; the repo has no mutable source with such a column, so the rejection rests on the rebuild argument. https://docs.getdbt.com/docs/build/snapshots (as of 2026-10; strong). That makes a snapshot a second source of truth a rebuild cannot recreate, against "raw is append-only, every fix downstream". MetricFlow type 2 joins also read the value at the start of a coarser window, and semantic models with type 2 dimensions "cannot currently contain simple metrics". https://docs.getdbt.com/docs/build/dimensions (as of 2026-10; strong).
- **Practice:** dbt's tutorial hashes the natural key with `dbt_utils.generate_surrogate_key` (blog above; strong for what it shows). **Pitfall:** adding a package for one macro breaks the package bar; the repo's readable composite text keys are debuggable. Record the departure so a reviewer sees it was chosen.
- **Alternatives rejected:** Data Vault (for many source systems and parallel teams; tier-3 sources only, https://datadriven.io/data-modeling/data-vault, as of 2026-10; weak) and Activity Schema (one event table; a 2021 dbt blog, https://www.getdbt.com/blog/activity-schema-data-modeling-with-a-single-table, with no 2025-or-later adoption evidence; weak).

## 4. Event data: sessions, replays and counters

**In plain terms.** Teams that model app events in dbt share one shape: a clean, de-duplicated event table first, then one table per entity (sessions, users), then summaries. The repo's staging, intermediate and marts already follow it. The event packages themselves (Snowplow, GA4, Segment) are tied to other warehouses or event formats and are not usable here. Two repo-specific problems have no published model: a save reload replays game days, and counters such as cash reset when that happens. The repo's save-lineage design (ADR 0011) already handles the first; the second needs a test.

**Technical detail** (lane 8 unless stated)

- **Practice:** Snowplow's unified package has four layers: base events (dedupe), views, sessions, users. https://docs.snowplow.io/docs/modeling-your-data/modeling-your-data-with-dbt/dbt-models/dbt-unified-data-model/ (as of 2026-10; strong). dbt-ga4 builds a cleaned event model, then per-event-type models, then session dimension and fact (https://github.com/Velir/dbt-ga4, as of 2026-10; moderate). **Pitfall:** these packages assume their own event schemas: GA4 is BigQuery-only; the Segment hub page shows an outdated version pinned `>=1.3.0,<2.0.0` (https://hub.getdbt.com/dbt-labs/segment/latest/, as of 2026-10); Snowplow needs Snowplow-shaped events. Borrow patterns, not packages.
- **Practice:** sessions are derived from events (Snowplow requires at least one page-view-type event for a session to exist; unified model page above, strong). Derive session bounds from ordered events and carry flags such as "first `seq` is 1" and "has a session-start event" (inference, weak). Roadmap 3b already starts the session dimension from events and left-joins `stg_sessions`; the flags are the new part. **Pitfall:** `make convert` already exits non-zero when a session's first `seq` is not 1, so the flag documents rather than detects in the pipeline as it stands.
- **Practice:** save reloads replay game days under a new session; lineage marks rows kept or abandoned and every count reads kept rows only. This is ADR 0011 and roadmap 3b already; no external source covers game-save replay (gap). **Pitfall:** a counter change computed with `lag()` across a reload produces a large false negative change; compute changes within one kept branch only, ordered by `seq`, and test that no change spans two branches (inference, weak).
- **Practice:** one model per event type keeps typed payloads narrow and testable; dbt-ga4 does the same (above). Lane 8 also proposes an `int_events__envelope` spine of envelope columns across all types. **Pitfall:** the repo already has `stg_envelope` (ADR 0016), which reads the envelope columns from every landed event type for the landed-event count; a second spine would duplicate it.
- **Practice:** a uniqueness test on `(session_id, seq)` after the dedupe is a second key independent of `event_id` (inference, weak). **Pitfall:** `make convert` already audits `seq` for gaps and repeats per session and stops the pipeline on one; the dbt test would repeat that check one step later.
- **Practice:** four clocks travel with every event (game date, company date, `emitted_at`, `received_at`); name the clock in every column. The repo's dbt rule already requires unit and clock suffixes (`.claude/rules/dbt.md`). **Pitfall:** ordering by `emitted_at` instead of `seq` breaks when two events share a tick; the contract guarantees `seq` order within a session.
- **Practice:** dbt treats `append` incremental as non-idempotent; `merge` and `delete+insert` are idempotent with a reliable `unique_key`. https://docs.getdbt.com/docs/build/incremental-strategy (as of 2026-10; strong). **Pitfall:** whether dbt-duckdb supports microbatch is disputed between lanes (section 16, conflict 6).

## 5. Time, the company calendar and year-over-year

**In plain terms.** A seasonal company needs one calendar table and year-over-year numbers that compare like with like. The repo already settled the calendar: the company date is stamped at the source (ADR 0014), and `dim_date` never contains November to February (ADR 0016). MetricFlow can name a custom year but cannot yet shift by one, so year-over-year stays in SQL, as ADR 0016 already decided. What the research adds is protection against misleading growth figures: show how many days and parks sit on each side of a comparison, and output nothing (not zero) when last year has no data.

**Technical detail** (lane 9 unless stated)

- **Practice:** MetricFlow needs a time spine model (`time_spine: standard_granularity_column`), dbt 1.9+, built with core `dbt.date_spine`; custom granularities such as a fiscal year are columns of the spine. https://docs.getdbt.com/docs/build/metricflow-time-spine (as of 2026-10; strong). Core `dbt.date_spine` avoids the `dbt_utils` package question. **Pitfall:** offsets and period-over-period on custom granularities "will be supported soon" (same page); a standard `offset_window: 1 year` shifts by Gregorian time, which on an 8-month game year lands on the wrong day (inference). Whether dbt 1.12 ships them was not checked.
- **Practice:** zero-fill only real zeros. `join_to_timespine: true` plus `fill_nulls_with: 0` writes a zero row for every spine day without data. https://docs.getdbt.com/docs/build/fill-nulls-advanced (as of 2026-10; strong). A spine without closed months avoids false zero months; `dim_date` already omits them, and the metric catalog already forbids zero months (roadmap NEXT 13b). **Pitfall:** how offsets behave over a spine with gaps is undocumented (gap).
- **Practice:** one physical date table joined under several roles (Kimball's role-playing dimension; techniques page above, moderate). The repo keeps game date and company date side by side on every fact (ADR 0016). **Pitfall:** lane 9 proposes a calendar keyed on park and game date that derives the company year inside dbt from a formula. That conflicts with ADR 0014 (the date is stamped at the source; intermediate validates it rather than deriving it) and ADR 0016 (`dim_date` keyed on company date). The records win; the lane's evidence for its design is weak.
- **Practice:** same-store comparison restricts both years to units present in both and to days present in both (https://blog.fulfil.io/retail-calendar-guide-2025-4-5-4-vs-4-4-5-calendar-systems-explained/, as of 2026-10; weak, single source). Carry the day count of both windows; emit null when the prior-year base is absent; for year-to-date, cut the prior year at the same day index (lane 9, standard SQL; weak). **Pitfall:** lane 9 would restrict company-wide year-over-year to parks open in both years. The catalog confirmed on 2026-10-03 keeps first-season parks in the company-wide metrics, beside like-for-like same-park metrics. The ruling stands; showing the park count on each side gives the reader the mix (and states the sample, invariant 7).
- **Practice:** DuckDB `TIMESTAMP` is naive; `TIMESTAMPTZ` is an instant, and zone-aware bucketing needs the ICU extension. https://duckdb.org/docs/current/sql/data_types/timestamp.html (as of 2026-10; strong). Wall-clock-hour metrics should convert `emitted_at` to one named zone in one model. **Pitfall:** no v1 mart uses the wall-clock hour (ADR 0016), and whether ICU loads offline in the agents' sandbox was not verified; this waits for the first wall-clock metric.

## 6. Testing and severity

**In plain terms.** dbt's advice is to test the assumptions that matter (keys, required fields, business identities, the shape of published tables), not to chase a test count. The repo's design already does this, including tests that deliberately break a model to prove a test notices.

**Technical detail**

- **Practice:** generic tests for keys and relationships, singular tests for one-offs, unit tests (dbt Core 1.8+) for complex logic, contracts for published shapes, model versions for breaking changes. https://docs.getdbt.com/docs/build/data-tests, https://docs.getdbt.com/docs/build/unit-tests, https://docs.getdbt.com/docs/mesh/govern/model-versions (as of 2026-10; strong). **Pitfall:** a unit test proves logic on its fixtures only; contracts check structure, not metric truth (same pages).
- **Practice:** errors for broken identities and public guarantees, warnings for reviewable observations; default severity is error. https://docs.getdbt.com/reference/resource-configs/severity and https://docs.getdbt.com/reference/data-test-configs (as of 2026-10; strong). **Pitfall:** `--warn-error` promotes unrelated warnings too.
- **Practice:** test the tests by planting bad rows; reconcile key metrics to an independent source of truth. https://github.com/dbt-labs/dbt-audit-helper/blob/main/README.md (as of 2026-10; moderate). A grain test plus a mutation test that plants a duplicate is the defense against mixed grains (lane 7). **Pitfall:** comparing two branches of the same transformation lets a fault agree with itself; ADR 0016 already requires two independent sides.
- **Practice:** constraints are adapter-dependent and separate from contracts. https://docs.getdbt.com/reference/resource-properties/constraints (as of 2026-10; strong). ADR 0016 keeps constraints out.
- **Note on version-tagged URLs:** several lane 2 URLs carry `?version=1.12` or `?name=Fusion&version=2.0`; none of the claims used here is version-specific beyond unit tests (1.8+).

Most well-known packages either do not list DuckDB as tested, are unmaintained, or need history the project does not keep. **Technical detail**

Lane 2 dates the release 2026-09-25; that date is unverified (the cited Hub and repository pages do not date it). https://hub.getdbt.com/dbt-labs/dbt_project_evaluator/latest/ and https://github.com/dbt-labs/dbt-project-evaluator (as of 2026-10; moderate). ## 8. CI, run artifacts and observability

**In plain terms.** The repo checks everything with one local command, which is the right size. Rebuilding only what changed and side-by-side output diffs pay off when builds get slow or reviews need them; neither is true yet. A small script that summarizes each run's results is a cheap way to show operational thinking, and DuckDB can read dbt's result files directly.

**Technical detail**

- **Practice:** slim CI selects changed nodes with `state:modified` and `--defer`s unselected parents to a baseline. https://docs.getdbt.com/reference/node-selection/state-selection and https://docs.getdbt.com/reference/node-selection/defer (as of 2026-10; strong). **Pitfall:** state selection cannot see data-only changes. ADR 0012 and roadmap NEXT 14 already reject slim CI.
- **Practice:** `manifest.json` holds the graph and `run_results.json` the outcomes and timings. https://docs.getdbt.com/reference/artifacts/run-results-json and https://docs.getdbt.com/reference/artifacts/manifest-json (as of 2026-10; strong). DuckDB can read both with its JSON reader and join them on `unique_id`, giving each failure with its upstream models and description, no package needed (lane 12; inference from the documented file shapes, untested). **Pitfall:** one run cannot show a trend; `--no-write-json` disables the artifacts and must never appear in the gate (lane 12).
- **Practice:** SQLFluff lints dbt SQL and can run in pre-commit. https://docs.sqlfluff.com/en/3.2.4/production/pre_commit.html (as of 2026-10; strong). **Pitfall:** two formatters make conflicting edits (lane 2; moderate). The gate already runs SQLFluff.
- **Practice:** Recce compares two local builds without a warehouse service (https://docs.reccehq.com/getting-started/oss-setup/, as of 2026-10; moderate). **Pitfall:** it needs a saved baseline build.
- **Practice:** artifact-consuming services (DataHub, OpenMetadata, OpenLineage with a local Marquez) can run self-hosted. https://docs.datahub.com/docs/generated/ingestion/sources/dbt and https://openlineage.io/docs/integrations/dbt/ (as of 2026-10; strong for what they do; lane 3). **Pitfall:** each is a service to operate (https://docs.open-metadata.org/v1.12.x/quick-start/local-docker-deployment, as of 2026-10); the dbt docs site covers lineage for this repo.

## 9. Documentation, exposures and the docs site

**In plain terms.** Every model and column gets a one-line description, and dbt turns them into a browsable website with a lineage graph. Declaring the showcase site as an "exposure" puts it on that graph. Reference projects that reviewers know (jaffle-shop, Cal-ITP) all publish such a site. The same descriptions, with unit, clock and the business question each model answers, are what an AI assistant needs to answer correctly.

**Technical detail**

- **Practice:** `description:` on models, columns and sources; doc blocks for long text; an `__overview__` block for the landing page; `dbt docs generate` builds a static site. https://docs.getdbt.com/docs/build/documentation (as of 2026-10; strong). **Pitfall:** the same page describes "dbt Docs v2 (dbt v2.0+)"; on 1.11.15 the classic `dbt docs generate` applies.
- **Practice:** exposures declare a downstream use with `owner`, `depends_on`, optional `url` and `maturity`; `dbt build -s +exposure:<name>` builds what one consumer needs. https://docs.getdbt.com/docs/build/exposures (as of 2026-10; strong; lanes 1 and 4). **Pitfall:** exposures are hand-maintained and drift; a gate check that every `obt_` table has one closes the gap (lane 4, weak).
- **Practice:** published docs sites are a shared trait of reference projects. https://docs.getdbt.com/faqs/Project/example-projects (as of 2026-10; strong). **Pitfall:** no hiring rubric names a docs site as a requirement (lane 6, gap).
- **Practice:** documentation for machines is the documentation humans need: grain, unit, clock. An independent paired study measured +17 to +23 points of text-to-SQL accuracy with semantic documentation. https://arxiv.org/abs/2604.25149 (as of 2026-04; moderate, abstract only). A Coalesce 2025 talk built an AI-searchable catalog from manifest descriptions written around the business problem each model solves (https://www.getdbt.com/resources/coalesce-on-demand, as of 2026-10; single source, page summary; lane 12). **Pitfall:** descriptions generated by an LLM from SQL risk plausible wrong text that later agents treat as truth (lanes 5 and 12; weak).

## 10. The semantic layer, MetricFlow and the dbt 1.12 change

**In plain terms.** A semantic layer writes each metric once so every tool computes it the same way. MetricFlow, dbt's open-source engine for that (Apache 2.0 since Coalesce 2025), runs locally on DuckDB. The repo's metric catalog is already written in the shape dbt 1.11 reads; dbt 1.12 changes that shape, and dbt provides a migration tool. Adding MetricFlow is a small, separate step after the marts exist; even then, year-over-year stays in SQL because MetricFlow cannot yet shift by a company year.

**Technical detail**

- **Practice:** with a semantic layer, keep marts more normalized; without one, denormalize. https://docs.getdbt.com/best-practices/how-we-structure/4-marts (as of 2026-10; strong). Build one semantic model per fact, joined through entities (https://docs.getdbt.com/best-practices/how-we-build-our-metrics/semantic-layer-3-build-semantic-models, as of 2026-10; strong; lane 7). **Pitfall:** until MetricFlow runs, the catalog formula and the `obt_` column are two copies joined by tests (ADR 0016). `fct_ride_day` to `dim_ride` to `dim_item` stays within the two-hop limit; a ratio across month and day facts (`revenue_per_visit`) is untested (lane 7, gap).
- **Practice:** dbt 1.6–1.11 read the legacy shape (top-level `semantic_models`, `measures`, `type_params`); dbt 1.12 nests `semantic_model` under each model and replaces measures with `type: simple` metrics; migrate with `dbt-autofix deprecations --semantic-layer`. https://docs.getdbt.com/docs/build/latest-metrics-spec and https://docs.getdbt.com/docs/build/semantic-models (as of 2026-10; strong). Time dimensions drop `type_params` in 1.12 (https://docs.getdbt.com/docs/build/dimensions, as of 2026-10; lane 9). **Pitfall:** no published date for how long the legacy shape stays supported after 1.12 (lane 4, gap).
- **Practice:** `pip install dbt-metricflow`; `mf list metrics`, `mf query`, `mf validate-configs`, `mf health-checks` run locally; `dbt sl`, saved-query exports and the hosted API need a paid platform account. https://docs.getdbt.com/docs/build/metricflow-commands (as of 2026-10; strong). Package facts: dbt-metricflow 0.15.0, released 2026-09-10, requires `dbt-core>=1.11,<1.13`, has a `dbt-duckdb` extra, Apache 2.0. https://pypi.org/pypi/dbt-metricflow/json (as of 2026-10; strong) and https://www.getdbt.com/blog/open-source-metricflow-governed-metrics (lane 3). **Pitfall:** the pairing with dbt-duckdb 1.11.0 has no compatibility statement; the repo's probe found semantic models crash plain `dbt parse` in the agents' sandbox unless a thread-pool swap is applied (`docs/FINDINGS.md`, 2026-10-02 and 2026-10-03; repo run, strong).
- **Practice:** a time spine model can be thin over `dim_date`; declare `company_year` as a custom granularity for the catalog (sections 5 and 9's time-spine page; strong for the mechanism). **Pitfall:** semantic model names may not contain double underscores; dimensions resolve only through entities; `offset_window` is not usable for the company year (section 5).
- **Version support:** dbt Core 1.11 is in critical support through 2026-12-18. https://docs.getdbt.com/docs/dbt-versions/upgrade-dbt-platform-version (as of 2026-10; **single source**). dbt Core v1 remains available beside dbt v2 (lane 3; section 13).
- **Open Semantic Interchange (now the Apache incubator project Ossie):** spec "actively evolving". https://ossie.apache.org/updates/osi-april-2026-community-update/ (as of 2026-04). dbt 1.12 reads Ossie files at version 0.1.0 or 0.1.1 only. https://docs.getdbt.com/docs/build/ossie-semantic-models (as of 2026-10; strong). **Pitfall:** a Snowflake snippet claims a finalized v1.0; treat the spec as pre-1.0.

**In plain terms.** The showcase site should display numbers, never define them. ## 12. The data-science layer

**In plain terms.** dbt is for building tidy tables, not for training models. dbt builds the feature table and the label table, a separate Python step trains and scores, and the scores come back as a declared source. This matters for the observational pricing model in v1 (NEXT 8).

- **Practice:** prefer SQL when equally clear; Python models are for what SQL cannot do. https://docs.getdbt.com/docs/build/python-models (as of 2026-10; strong). dbt-duckdb runs Python models in-process. https://github.com/duckdb/dbt-duckdb (as of 2026-10; strong). **Pitfall:** training inside the dbt build couples it to `make check`'s runtime (lane 4, inference); dbt's sample mode ignores Python models, so it cannot stand in for validating them (https://docs.getdbt.com/docs/build/sample-flag, as of 2026-10; strong; lane 3).
- **Practice:** feature rows carry a snapshot date; labels come from after it; time-based splits. https://motherduck.com/docs/cookbook/dbt-churn-prediction/ and https://feast.dev/blog/feast-dbt-integration (as of 2026-10; moderate). **Pitfall:** leakage; a singular test that no feature's source date exceeds its snapshot date encodes the rule (inference).
- **Practice:** load predictions as a `sources:` entry with tests and declare the model as an `ml` exposure (inference, weak). **Pitfall:** results that do not state their sample.

## 13. Ecosystem, scale and engines (Mesh, Fusion, orchestration, DuckDB, lakehouse formats, portability)

**In plain terms.** Large dbt teams split work into several projects with ownership rules (dbt Mesh), schedule runs with an orchestrator, and feed a metadata catalog. Each answers a problem of many teams; none exists in a one-project portfolio, and imitating them reads as imitation, not scale. dbt's newer engine, Fusion, is now generally available as dbt v2; it is mostly compatible but stricter, and moving to it is a separate, later question. Lane 10 adds three local questions: keep one DuckDB file per environment (yes), what "portable SQL" can honestly be claimed ("DuckDB-first" only), and whether a lakehouse format is needed (not now).

**Technical detail** (lane 3 unless stated)

- **Practice:** Mesh uses `private`, `protected` and `public` access, contracts and versions to mark project boundaries; cross-project `ref` needs the dbt platform's metadata service and an Enterprise tier. https://docs.getdbt.com/docs/mesh/govern/model-access and https://docs.getdbt.com/docs/mesh/govern/project-dependencies (as of 2026-10; strong). **Pitfall:** Mesh adds maintenance and deployment coordination (https://docs.getdbt.com/best-practices/how-we-mesh/mesh-5-faqs, as of 2026-10; strong). Use groups only when they mirror real ownership.
- **Practice:** Fusion is the engine behind generally available dbt v2; dbt Core v1 remains available. https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v2 (as of 2026-10; strong for the page, single lane). DuckDB support in the v2 CLI is generally available (https://docs.getdbt.com/docs/supported-data-platforms, as of 2026-10). **Pitfall:** v2 parses more strictly and removes deprecated syntax; each package and adapter plugin needs its own check; the standard dbt distribution carries product-license terms, while a separate dbt OSS distribution is Apache 2.0 (https://www.getdbt.com/licenses-faq, as of 2026-10). This corrects the first draft's "Fusion (preview)", which came from 2025 sources.
- **Practice:** Core 1.9 added microbatch; 1.10 added sample mode and initial catalog support for table formats such as Iceberg; 1.11 added function resources. https://www.getdbt.com/blog/dbt-core-v1-9-is-ga, https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v1.10, https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v1.11 (as of 2026-10; strong). **Pitfall:** function resources list BigQuery, Snowflake, Redshift, Postgres and Databricks, not DuckDB (https://docs.getdbt.com/docs/build/udfs, as of 2026-10; strong; lane 12); dbt-duckdb documents a `unique_key` limitation with microbatch (https://github.com/duckdb/dbt-duckdb, as of 2026-10).
- **Practice:** microbatch suits large time series with reliable event time; there is no universal row-count threshold for incremental models; DuckDB's row-group and file-size guidance is format advice, not a dbt threshold. https://docs.getdbt.com/docs/build/incremental-microbatch and https://duckdb.org/docs/current/guides/performance/file_formats (as of 2026-10; strong). **Pitfall:** inventing a production-scale need; ADR 0016's 5-minute trigger is the honest one.
- **Practice:** locally runnable orchestration exists (Dagster dbt assets, Airflow with Astronomer Cosmos). https://docs.dagster.io/integrations/libraries/dbt and https://astronomer.github.io/astronomer-cosmos/getting_started/oss-quickstart.html (as of 2026-10; strong). **Pitfall:** scheduler, deployment and environment concerns; the roadmap already holds an orchestrator as a LATER bet until `make` is outgrown. Reverse ETL (Multiwoven, https://github.com/Multiwoven/multiwoven) has no consumer here.
- **Practice (lane 10):** dbt-duckdb runs dbt against a local DuckDB file; read event Parquet through sources with `external_location`, and use the `external` materialization only for deliberate CSV, JSON or Parquet exports. https://github.com/duckdb/dbt-duckdb (as of 2026-10; strong). **Pitfall:** external models are full-refresh only, with no incremental strategies; Python models run in the local dbt process and are distinct from dbt Core 1.11's Python UDFs (listed for Snowflake and BigQuery, not DuckDB; https://www.getdbt.com/blog/dbt-core-v1-11-is-ga, as of 2026-10); the 1.11.0 adapter release changed how partition column names are emitted, so names with spaces or special characters need explicit quoting (https://github.com/duckdb/dbt-duckdb/releases, as of 2026-10). Adapter releases are irregular (1.10.0 in 2025-11, 1.10.1 in 2026-02, 1.11.0 in 2026-08), so the repo's pinned stack is its own tested target (https://github.com/duckdb/dbt-duckdb, as of 2026-10).
- **Practice (lane 10, lakehouse):** keep the local DuckDB file; revisit DuckLake (spec v1.0, 2026-04; metadata in a SQL catalog, data in Parquet) when sharing, snapshots or Parquet-backed tables become real needs, and Iceberg when Iceberg catalogs and engines become a requirement. https://ducklake.select/release_calendar, https://ducklake.select/docs/stable/specification/introduction and https://duckdb.org/docs/current/core_extensions/iceberg/overview (as of 2026-10; moderate). MotherDuck runs dbt-duckdb through an `md:` connection and offers hosted DuckLake (https://motherduck.com/product/ducklake/, as of 2026-10). **Pitfall:** DuckDB lists its DuckLake and Iceberg extensions as secondary, best-effort (https://duckdb.org/docs/current/core_extensions/overview); direct Iceberg scans are read-only and writes need a REST catalog (https://duckdb.org/docs/current/core_extensions/iceberg/writing_to_iceberg); MotherDuck's managed DuckLake was public preview and adds cloud credentials; the next DuckLake spec and extension release was tentatively 2026-10-21, so pin versions if experimenting (all as of 2026-10).
- **Practice (lane 10, portability):** shared SQL uses dbt's cross-database macros (`dbt.date_trunc`, `dbt.datediff`, `dbt.cast`, `dbt.safe_cast`, type macros such as `dbt.type_string()`), `adapter.dispatch` where an operation needs per-adapter code, and DuckDB-only syntax (`read_parquet`, `list_*`, `struct_*`, `GROUP BY ALL`, Python models) only at the source and export edges. https://docs.getdbt.com/reference/dbt-jinja-functions/cross-database-macros and https://docs.getdbt.com/reference/dbt-jinja-functions/dispatch (as of 2026-10; moderate). **Pitfall:** the macros still have adapter-specific limits (some date parts are unsupported on some adapters), and Snowflake and BigQuery enforce constraints differently (https://docs.getdbt.com/reference/resource-properties/constraints, as of 2026-10). No run on a second adapter exists for this repo, so call the stack "DuckDB-first", never "portable" (a reviewer expectation inferred from dbt's guidance; weak).

## 14. AI-native and agent-friendly architecture

**In plain terms.** Two different AI questions apply. First, can an AI answer business questions correctly? The measured lever is a semantic layer: the AI picks named metrics instead of writing free SQL, and refuses what the metrics cannot answer; that is the existing LATER bet. Second, can AI agents safely build and change this dbt project, which is how most of it is written? Here the research found no proof of which instructions help, but a clear direction: keep agent instructions short, give agents a list of safe commands, turn rules into deterministic checks, and measure agents with fixed tasks whose right answers are known. The repo already has most ingredients (rule files, one gate, acceptance scenarios, mutation tests). Hosted dbt agents and AI judgments that pass or fail a build are not usable or not trustworthy yet.

**Technical detail: answering questions (lanes 5 and 12)**

- **Practice:** dbt Labs' benchmark (2026-04-07): raw SQL on modeled tables 84–90%, semantic layer 98–100% only after the authors added three models so all 11 questions could be answered (before that: 72.7% overall and 0% on too-many-hop questions), with explicit errors for out-of-scope questions. https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026 (as of 2026-04; vendor-run, single source). **Pitfall:** the independent study (https://arxiv.org/abs/2604.25149, as of 2026-10) found 67.7–68.7% with a 4 KB semantic documentation file, not an executable MetricFlow layer, so the two figures are not directly comparable; the semantic layer scored 0% on "too many hops" questions in dbt's own run.
- **Practice:** evaluation sets of verified question-and-query pairs are the vendor norm (https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst-evaluations and https://www.databricks.com/blog/building-confidence-your-genie-space-benchmarks-and-ask-review, as of 2026-10; moderate to strong). For the chat, a small DuckDB table of question, expected metric call, expected value and sample, plus a log of runs, scores by exact equality (lane 12; weak-moderate). **Pitfall:** relative dates make ground truth go stale. Paradime's `dbt-llm-evals` scores AI output with warehouse AI functions on Snowflake, BigQuery and Databricks only, not DuckDB (https://github.com/paradime-io/dbt-llm-evals, as of 2026-10; moderate); lanes 11 and 12 disagree on whether it is on the package hub.

**Technical detail: agents building the project (lanes 11 and 12)**

- **Practice:** a short repo instruction file plus metadata the agent can inspect. dbt Labs' own docs repository carries an `AGENTS.md` (about 436 lines, a contributor and style contract, not a model-safety contract). https://github.com/dbt-labs/docs.getdbt.com/blob/current/AGENTS.md (as of 2026-10; moderate). dbt's structured-context article lists what an agent should read (lineage, run artifacts, semantic definitions, tests, contracts) and a three-step flow: ingest context, change and validate locally, validate through tests and CI. https://www.getdbt.com/blog/bring-structured-context-to-agentic-data-development-with-dbt (as of 2025-12; moderate, vendor). **Pitfall:** no source measures which instruction content improves change safety (lanes 11 and 12; emerging practice, weak). A second instruction file beside `CLAUDE.md` can drift from it.
- **Practice:** inspection needs no new tool: `dbt parse` writes `target/manifest.json`, `dbt ls --select <selector> --output json` lists nodes. https://docs.getdbt.com/reference/artifacts/run-results-json (as of 2026-10; strong). An agent-safe commands list (parse, list, a selected build against a development or scratch copy of the DuckDB file; never a published file; never edit raw data or weaken a test) is lane 12's synthesis (weak). **Pitfall:** practitioner guardrails (read-only profiles, dry runs) have no primary dbt source (gap).
- **Practice:** the local dbt MCP server (`uvx dbt-mcp`) needs only `DBT_PROJECT_DIR` and `DBT_PATH` for its CLI tools (build, run, test, compile, parse, docs, clone, show, list); its code-generation tools also work locally. Allowlist mode is confirmed: `DBT_MCP_ENABLE_DBT_CLI`, `DBT_MCP_ENABLE_TOOLS`; deny mode: `DISABLE_DBT_CLI`, `DISABLE_DBT_CODEGEN`, `DISABLE_TOOLS`; per-tool settings win over group settings; `DBT_CLI_TIMEOUT` defaults to 60 seconds. https://docs.getdbt.com/docs/dbt-ai/setup-local-mcp and https://docs.getdbt.com/docs/dbt-ai/mcp-available-tools (as of 2026-10; strong). **Pitfall:** CLI tools can modify models and warehouse objects; what its "read-only mode" covers is unconfirmed; DuckDB has no read-only roles, so agents need a copied file; a full rebuild may exceed the default timeout; its release date was not checked against the bar.
- **Practice:** dbt Labs' agent skills (Apache 2.0) include adding unit tests, maintaining documentation, running dbt commands and building the semantic layer, plus platform-only and migration skills. https://github.com/dbt-labs/dbt-agent-skills (as of 2026-10; moderate; skill bodies unread). **Pitfall:** a wholesale install can contradict `docs/CONVENTIONS.md` (for example, incremental models or packages). Lane 12 advises copying useful parts into `.claude/rules/dbt.md` after reading them, rather than installing; this replaces the first draft's "install selected skills".
- **Practice:** evaluate coding agents with fixed tasks. dbt's A/B evaluator in the skills repo runs scenarios with variants (skills on or off, MCP servers, model versions) and records tool counts, cost and modified files; it grades with an LLM or by hand. https://github.com/dbt-labs/dbt-agent-skills/blob/main/evals/README.md (as of 2026-10; moderate). This repo can grade deterministically: tasks from the acceptance scenarios, traps from the mutation tests (do not weaken a test, notice a missing tenths conversion, refuse an out-of-scope request), pass meaning `make check` green, only expected files changed, no forbidden pattern, result values equal on the committed sample; three runs per task, pass rate per model and instruction version (lane 12; inference, weak-moderate). **Pitfall:** agents are non-deterministic and cost per run is unmeasured; one run proves nothing.
- **Practice:** AI output is a proposal, never a verdict. An LLM code-review study found inaccurate approvals up to 44.4% and recommends human review (https://arxiv.org/pdf/2505.16339v1, as of 2025-05; before the 2025-07 window, background only). No vendor-neutral pattern for LLM-generated docs or tests in dbt CI was found (lane 11). **Pitfall:** a false approval is worse than a false alarm; the repo's blind reviewers already play the advisory role.

- **Record shape:** the first draft judged a separate AI ADR unwarranted. ## 15. How the project reads to a reviewer

**In plain terms.** Reviewers judge whether you know your numbers are right, not how many tools you used. A page explaining what each test catches, a page of failure modes and how they would be caught, and a page of what was deliberately not built read as senior. AI use is accepted when the decisions and checks are visible. This evidence is the weakest of the lanes.

- **Practice:** interviews probe grain, the tests that prove it, and what breaks a model. https://www.techinterview.org/post/3233476973/dbt-analytics-engineering-interview-questions/ (as of 2026-10; weak, single source). **Pitfall:** no published hiring rubric for dbt portfolios was found.
- **Practice:** reference projects share a docs site, tests and CI, an enforced style and written conventions. https://github.com/dbt-labs/jaffle-shop (as of 2026-10; strong). **Pitfall:** copying team-scale orchestration, Mesh or packages into a one-person repo reads as imitation (lanes 3 and 6, inference).
- **Practice:** disclose AI use in one line; show decisions, rejected outputs and checks. https://www.artech.com/blog/ai-assisted-portfolio-credibility/ (2026-03) and https://provn.co/blog/2026/06/show-ai-judgment-portfolio (2026-06) (moderate). A pass-rate table from a coding-agent evaluation would be concrete evidence of the same judgment (inference, weak).
- **Inference (weak):** mutation tests and metric-identity tests may read as gold-plating unless the README says what each catches; a bus matrix and a "do not sum across days" note are standard Kimball signals a reviewer recognizes (lane 7).

## 19. Decisions and the project owner's rulings (2026-10-06)

**Bottom line.** The project owner accepted the recommended option (A) on all 19 decisions; none reversed an earlier ruling. D18 and D19 come from lane 10. Rulings that need the owner's later sign-off say so.

- **D1, extras for the staging slice (3a):** all five join existing 3a tickets (macro argument docs and `validate_macro_args` if it parses on dbt 1.11.15, else dropped and noted; stored failures and a clear name for the differing-duplicate warning; `not_null` on the raw envelope with `unique(event_id)` only after the dedupe; a schema-macro safety comment; three conventions sentences on departures from dbt's style guide).
- **D2, how contract-generated sources are produced:** 3a's first ticket probes the `dbt-sources` export; it is used if the output carries the Parquet location and descriptions, else a small generator script; contracts stay the single source.

- **D12, shape of the ADRs:** two ADRs, 0019 for dbt practices (supersedes parts of 0016) and 0020 for agent working rules (D11, D16, D17 and "AI output never passes or fails a build"; labeled emerging practice with a revisit point); both provisional pending the owner's review.
