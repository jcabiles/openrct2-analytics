# Which tool serves the showcase website, and how the README stays in step with it — research findings
status: research complete; blind-reviewed three times, all thirty-three findings folded in (`docs/ai-dlc/ledger/showcase-site-tool.md`) · date: 2026-10-03 · initiative: park-company (roadmap NEXT 15, "How does a reader explore the company and the stack?", research step only)

## Bottom line
- **Recommended tool: Observable Framework** (Observable's open-source static-site generator for data apps and reports, ISC licence). **The deciding criterion is built-in dashboards:** every dashboard group in the roadmap's v1 list (executive reporting, ride profitability, stall profitability, and the stack's "interactive dashboards") needs charts over mart rows, inputs that filter them by park, company year, ride or stall, and a browser DuckDB to read the marts, and Framework is the only finalist with charts (Observable Plot), inputs, grid layouts and a client for DuckDB-WASM (DuckDB compiled to run inside a web page) built in (section 1.1). Its pages are markdown, and its charts run in the reader's browser over Parquet copies of the dbt marts. **Gain:** the least hand-written chart code of the three finalists, and no new toolchain binary. **Cost:** its maintainer has moved development to a new product, so it is supported but not developed (one patch release, 1.13.4 on 2026-03-02, in the last seventeen months), and in March 2026 recommended that Framework users migrate to Notebook Kit, a technology preview; it sends usage data unless `OBSERVABLE_TELEMETRY_DISABLE` is set; its narrative features are plainer than Quarto's; and the browser libraries its pages import are resolved against the npm registry and downloaded from the jsDelivr CDN at build time, outside `package-lock.json`. Pages can import libraries by bare name from the locked `node_modules` instead, except the apache-arrow library that the built-in DuckDB client loads at its latest release; that import is either replaced by a hand-written DuckDB loader or accepted as a named risk, which is the project owner's decision (section 1.1, ADR 0015 "Needs owner decision").
- **How the recommendation moved under review.** The first draft recommended Quarto and dismissed Framework as stalled; the first blind review showed that claim overstated, and Framework took the lead. The second review showed that Framework's lead on lockability (whether every dependency is pinned so that a clean build reproduces it) was unsupported, and that Quarto has a documented client-side dashboard format. The honest re-score (section 1.1) keeps Framework first on dashboards, puts **Eleventy first on lockability**, and leaves Quarto first only on narrative pages. **Eleventy replaces Quarto as the fallback.** Two adoption acceptance tests apply to whichever tool is adopted: the site reproduces from an empty download cache after upstream releases change, and every page loads with networking disabled. Eleventy is built to meet both; Quarto trails on lockability, and its offline behaviour is an unverified risk resting on 2022 evidence (section 2.2). If the project owner weighs lockability above dashboards, Eleventy wins outright; that is the one judgment call in this ranking.
- **The 2026-09-27 default, Evidence, changed under the project.** On 2026-08-26 Evidence replaced its npm framework with Evidence Core, a binary installed by a `curl | sh` script that sends usage data by default and is documented as self-hosted through a Docker server. Its flat-file (Parquet) connector is documented under Studio's managed warehouse, so whether Core can read local Parquet without a Studio account is **unverified**. The old npm framework's last release was 2026-02-06. Evidence Core is checked again when the site build starts (section 2.1).
- **One source of text for the README and the site.** The story lives once, in five markdown files under `docs/showcase/story/` (drafted in this change). `README.md` is generated from them byte for byte; the README's run instructions come from the "Run it yourself" section of `docs/showcase/story/README.md`; each site page that carries a story file contains only its include directive, and a source check fails on any other text there and unless each story file is included exactly once; chart titles and annotations come from the story files or the metric catalog, never typed into page code; and the story files' root-relative links are resolved in both outputs. **Gain:** both outputs are checked at the source, without comparing rendered HTML, and with no new dependency. **Cost:** about 150 lines of standard-library script and tests (section 4).
- **Every business result in a chart, table or the README is a mart column, traced to the game.** A committed mapping gives each published business result its mart query, its in-game source and the dbt reconciliation test that fails `make check` when the modeled value drifts from that source. Charts are declarative specs that show mart rows as delivered, with no arithmetic in chart code, and a source check enforces it. Explanatory numbers in story text, such as game-calendar constants and measured plugin timings, pass when their sentence cites a source. `make check` also rebuilds the Parquet files the site reads and compares them with the served copies by row count and hash (section 3.4).
- **Direct querying needs no site tool.** The pinned `duckdb` Python package opens the warehouse read-only, and the DuckDB UI starts from it with `CALL start_ui()` (section 3.1).
- **Semantic layer and AI chat.** The metric catalog (roadmap NEXT 13, the governed metric definitions) stays the only definition of each metric. Every candidate needs a server-side process to hold a chat's API key, so the AI chat stays a separate later service (sections 3.2 and 3.3).
- **What waits on the project owner:** approving Observable Framework as an npm dependency. A short spike then confirms that it builds inside the agents' sandbox and in CI, that the site reproduces from an empty download cache after upstream releases change, and that every built page loads with networking disabled; the project owner also decides how to treat the one unpinnable import. ADR 0015 records the proposal and maps every v1 requirement the site must carry to a page and an acceptance check.

## How this was produced
One research lane ran on 2026-10-03: a Claude agent with web search, reading official documentation, project repositories, release pages and dated articles. Release dates come from the npm registry (read with `npm view`, which installs nothing) and from PyPI wherever a page summary disagreed with them. No candidate tool was installed or trialled; the brief forbids it, so install sizes and sandbox behaviour are untested (section 7).

A blind review by a model from another vendor then raised eleven findings (`docs/ai-dlc/reviews/showcase-site-tool-1-sol.md`); all were accepted and folded in on 2026-10-03. During that pass the published package source of Observable Framework 1.13.4 and Eleventy 3.1.6 was read from their npm registry tarballs, unpacked in a scratch folder outside the repo; nothing was installed. Web pages could not be fetched in that pass, so claims that rest only on the review's links say so.

A second blind review from the same outside vendor then raised eight more findings (`docs/ai-dlc/reviews/showcase-site-tool-2-sol.md`); all were accepted and folded in on 2026-10-03. During that pass the published package source of Framework 1.13.4 was read again from its npm registry tarball, unpacked in a scratch folder outside the repo, to check how it resolves browser imports and DuckDB extensions; nothing was installed. Web pages could not be fetched in that pass either, so Quarto's dashboard page, Framework's import and DuckDB pages, and the legacy Evidence documentation host rest on the review's links, and the source code where it applies.

A third blind review from the same outside vendor raised thirteen major findings and one optional note (`docs/ai-dlc/reviews/showcase-site-tool-3-sol.md`); all were accepted and folded in on 2026-10-03. It removed an unsourced count of chart views from the deciding criterion, reworded Quarto's offline ranking as an unverified risk, replaced the two-build reproducibility test with an empty-cache test, tied each published business result to its in-game source, added a check against chart calculations, scoped the number rule, and cut the story drafts to at most 200 words of body each. Nothing was installed or re-fetched in that pass.

Each claim carries its source URL and an "as of" date; "as of 2026-10" means the page was read then and carried no date of its own. Evidence strength: **strong** (several primary sources agree, or the tool's own source code), **moderate** (one primary source, or several secondary ones), **weak** (one secondary source, a vendor page making a claim about itself, or inference). Each tool ends with a verdict: **recommended**, **fallback**, **re-check later**, or **rejected**, with the reason.

### 1.1 The three static finalists on the same criteria

**Framework leads on dashboards, the deciding criterion, so it is recommended; Eleventy leads on lockability and is the fallback; Quarto leads only on narrative pages.** The roadmap's v1 list names the dashboards; the table below compares the finalists against it. Dashboards are where the finalists differ most in how much code the project must write and test. Quarto's narrative strength is real, but five plain story files need no cross-references or citations.

| v1 dashboard requirement (roadmap, "v1 is done when") | What it needs from the tool | Observable Framework | Quarto | Eleventy |
|---|---|---|---|---|
| Executive reporting: year-over-year visitors, revenue, profit and operating costs per park and for the company; monthly and annual P&L; visitor growth; average park rating | Charts over mart rows; inputs for park and company year | Plot, inputs and grid layouts built in; inputs re-run the charts that use them | Charts and inputs through OJS cells in its dashboard format | Every chart, input and its wiring hand-written |
| Ride profitability: profit by ride type, ratings, age and coaster statistics; popularity against ratings; pricing model | Scatter and bar charts over mart rows; inputs for ride type and park | As above | As above | As above |
| Stall profitability: units sold per stall; drivers of stall profit, including weather | Charts over mart rows; inputs for stall and park | As above | As above | As above |
| The stack: interactive dashboards over DuckDB | A browser DuckDB that reads the mart Parquet | DuckDB client and SQL blocks built in; it loads apache-arrow at its latest release, so a locked build replaces it with a hand-written loader (ADR 0015, "Needs owner decision") | DuckDB-WASM imported in an OJS cell | DuckDB-WASM loader hand-written |
| The stack: direct DuckDB query access | Read-only `duckdb` commands (section 3.1) | Not a site-tool feature | Not a site-tool feature | Not a site-tool feature |

**The recommendation holds on this comparison, by a narrower margin than an earlier draft claimed.** Every dashboard group needs the same three things, charts over mart rows, filtering inputs and a browser DuckDB, and Framework is the only finalist with all three built in. Quarto has the first two through OJS; Eleventy has none. If the project owner chooses the locked route, Framework's lead over Eleventy rests on its built-in charts, inputs, reactive layouts and page loaders, and over Quarto on its lockable npm package.

Two requirements are kept apart. **Runs locally** is the roadmap's requirement (NEXT 15): the site is served from this machine with no hosted service behind it, and all three finalists meet it. **Network-free viewing** is stricter: every built page loads with networking disabled. It is an adoption acceptance test for whichever tool is adopted (section 7), not a ranking requirement, because a site that runs locally may still fetch a library from a CDN when a page opens.

## 2. Tool by tool

### 2.1 Evidence (legacy npm framework, and Evidence Core) — re-check later
**In plain terms.** Evidence lets an author write a page in markdown with SQL queries and chart components, then builds a website. It was chosen on 2026-09-27 as a business-intelligence-as-code signal that a recruiter could open without installing anything. In August 2026 the company replaced that framework with a new one, Evidence Core, which works differently. The old one is no longer where the vendor puts its effort, and the new one is too young, too server-oriented, and too unclear about local data to judge yet.

**The evidence.**
- Evidence Core was announced on 2026-08-26 as "the framework that powers Evidence Studio". It is MIT-licensed, adds live queries ("its components query the underlying database"), reusable metrics, a stricter syntax and a single CLI binary, and its projects "build into Docker containers and include basic authentication"; a `migrate` command moves legacy projects (https://evidence.dev/blog/evidence-core, 2026-08-26). **Moderate** (vendor about itself).
- The CLI installs with `curl -fsSL https://evidence.studio/install.sh | sh`. Its commands include `login`, `dev`, `upgrade`, `telemetry` and `serve`, and it sends anonymous usage events unless `EVIDENCE_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1` is set (https://docs.evidence.dev/cli, as of 2026-10). **Strong.**
- The documentation disagrees with itself on hosting. The front page says Core "builds to a static site you can self-host anywhere" (https://docs.evidence.dev/, as of 2026-10). The self-hosting page says "the image runs `evidence serve` … hardened as a production server", protected by HTTP Basic Auth (https://docs.evidence.dev/self-host/, as of 2026-10). **Moderate.**
- The flat-file connector (CSV, JSONL, Parquet) is documented under the Evidence warehouse, Studio's managed warehouse (https://docs.evidence.dev/evidence-warehouse, cited by the review, not re-fetched). Core's CLI connection documentation does not establish a local-file connector (https://docs.evidence.dev/cli/connections, cited by the review). Studio's models run on ClickHouse table engines in a Google Cloud region (https://docs.evidence.dev/core-concepts/models, as of 2026-10). **Moderate; Core reading local Parquet or a DuckDB file without Studio: unverified.**
- Core's metrics live in `metrics/*.yaml` with no mention of dbt or MetricFlow (https://docs.evidence.dev/core-concepts/metrics, as of 2026-10), but its components can also consume data directly (https://docs.evidence.dev/core-concepts/components, cited by the review). Core has partials, `{% partial file="/partials/x" /%}`, with passed variables; the legacy syntax was `{@partial "x.md"}` (https://docs.evidence.dev/core-concepts/partials, as of 2026-10). **Strong.**
- The migration guide lists what does not carry over from legacy projects: templated pages, `sources/` SQL, Svelte components, JavaScript expressions in pages, and some chart types (https://docs.evidence.dev/migration-guide, as of 2026-10). **Strong.**
- The legacy npm package `@evidence-dev/evidence` was last published as 40.1.8 on 2026-02-06; the release before that was 2025-11-15. It builds with `@sveltejs/adapter-static`, and its query layer bundles `@duckdb/duckdb-wasm` ^1.30.0 (npm registry, read 2026-10-03). **Strong.**
- The repository is active: commits on 2026-09-29 to 2026-10-02 include hosted-product features such as organisation-scoped uploads (https://github.com/evidence-dev/evidence/commits/main, as of 2026-10). **Strong.**
- Public portfolio stacks of the dlt, DuckDB, dbt and Evidence kind exist, for example https://github.com/Ddscully/dlt-dbt-duckdb-evidence (as of 2026-10). **Weak, single example.**

**Best practices.** In the legacy framework, source queries ran at build time (`npm run sources`) into Parquet, and pages queried that Parquet in the browser. That pattern keeps a site static and fast.

**Pitfalls.** Adopting legacy now means building on a line its maker has moved off, with a migration that drops features. Adopting Core now means a five-week-old tool that cannot be pinned by `package-lock.json` or `uv.lock`, that phones home unless told not to, whose own pages disagree about whether it is static, and whose local-data ability is unverified. Whether its metric files would add a second metric definition depends on that check: if components can read the exported marts directly, the metric layer can stay unused.

**Verdict: re-check later.** The legacy framework is rejected. Evidence Core is re-checked when the site build starts (after the marts, step 4). It becomes a contender if a Core project, with no Studio account and no managed warehouse, reads the local mart Parquet files and builds offline; offers a static export or a local server that needs no account; and ships versioned binary downloads that can be pinned with checksums.

### 2.2 Quarto — third, not adopted
**In plain terms.** Quarto turns markdown documents into websites, reports and dashboards. It is common in data science, which matches the audience. It writes prose best of all the candidates and can include one file inside another, but its interactive pages may contact external hosts when opened (unverified on a current build), and it adds a binary that no lockfile pins.

**The evidence.**
- Quarto is MIT-licensed (https://github.com/quarto-dev/quarto-cli, as of 2026-10). The stable release is 1.10.18 (2026-07-24, https://pypi.org/project/quarto-cli/), and 1.11 previews shipped on 2026-07-28, 2026-09-02, 2026-09-03, 2026-09-09 and 2026-09-17 (https://github.com/quarto-dev/quarto-cli/releases, as of 2026-10). **Strong.**
- Quarto has a documented dashboard format. Dashboards can use "Observable JS for client-side interactivity", which needs no server, while Shiny-based interactivity "requires a server for deployment" (https://quarto.org/docs/dashboards/interactivity/, as of 2026-10). **Strong.**
- Includes use `{{< include _file.qmd >}}`. Included files take an underscore prefix so they are not rendered alone, relative references "resolve based on the directory of the main file", and an include must sit alone on its line (https://quarto.org/docs/authoring/includes.html, as of 2026-10). **Strong.**
- A `README.qmd` with `format: gfm` renders to `README.md` (https://quarto.org/docs/output-formats/gfm.html, as of 2026-10). **Strong.**
- Quarto publishes its own list of external hosts that HTML output contacts, including those used by OJS pages (https://quarto.org/docs/advanced/html/external-sources.html), and an open issue describes runtime downloads that prevent offline use (https://github.com/quarto-dev/quarto-cli/issues/1412). The issue reports Quarto 1.0.23 in 2022 and describes a possible local-copy workaround, so neither source shows that a configured 2026 build fails an offline page load. Both are cited by the reviews and were not re-fetched. **Moderate, and dated.**
- The PyPI package "downloads required Quarto binary files from GitHub during installation" (https://pypi.org/project/quarto-cli/, as of 2026-10). This repo already rejected dbt-core 1.12 for that same behaviour, because it fails in a sandboxed build (`pyproject.toml` comment). **Strong.**
- DuckDB-WASM loads most simply from jsDelivr bundles, and the files can be self-hosted for offline use (https://duckdb.org/docs/current/clients/wasm/instantiation, as of 2026-10). **Strong.**
- Reading a relative Parquet path through DuckDB in OJS was a bug in 2022, fixed in Quarto 1.3 (https://github.com/quarto-dev/quarto-cli/issues/3630, 2022-12). Community write-ups note that the browser loads the whole Parquet file on each page open (https://forum.posit.co/t/using-quarto-with-ojs-and-duckdb/190311, as of 2026-10). **Weak.**

**Pitfalls.** Python code cells would need Jupyter, which brings new packages, so data preparation belongs in a `make` step instead. Network-free viewing is an unverified risk resting on 2022 evidence; the offline page-load test settles it if Quarto ever becomes the fallback. Install through the PyPI wrapper is ruled out. Pandoc rewrites markdown formatting on output, which makes a Quarto-rendered README noisy to diff (inference from how the gfm writer works). **Moderate.**

**Verdict: third, not adopted.** Its documented dashboard format puts it second on the deciding criterion, but it ranks last on lockability, and its network-free viewing is an unverified risk, so Eleventy is the safer fallback. It returns only if both Framework and Eleventy fail their spikes, and then under the same two acceptance tests, including the offline page load.

### 2.3 Observable Framework — recommended; Notebook Kit — rejected
**In plain terms.** Framework turns markdown pages into a static site with charts and DuckDB queries that run in the reader's browser. Its maker has moved new development to a notebook product, but Framework is still supported and still ships patches. Its build copies the npm libraries a page imports into the site, but it picks their versions from the network at build time, outside the lockfile.

**The evidence.**
- Mike Bostock, Framework's maintainer, wrote: "Framework will continue to work and be supported … but our development efforts are currently focused on Notebooks and Canvases" (https://github.com/observablehq/framework/discussions/2022, 2025-08-28). **Strong.**
- `@observablehq/framework` 1.13.4 was published 2026-03-02, after 1.13.3 on 2025-04-16; the licence is ISC, it has 44 direct npm dependencies, and it needs Node 18 or later (npm registry and package metadata, read 2026-10-03). **Strong.**
- Framework runs "client-side SQL using DuckDB" over CSV, TSV, JSON, Arrow, Parquet "and DuckDB database files" (https://github.com/observablehq/framework/blob/main/docs/sql.md, as of 2026-10). Page loaders are scripts such as `.md.js` or `.md.py` that emit markdown pages (https://observablehq.com/framework/page-loaders, as of 2026-10; present in the 1.13.4 source, `dist/loader.js`). **Strong.**
- In the 1.13.4 source, imports of npm libraries resolve to `/_npm/` paths inside the built site and are filled from `https://cdn.jsdelivr.net/npm/` into a local cache at build time (`dist/npm.js`). Versions are chosen at that moment: an exact version is used as written, and anything else is resolved against the npm registry; DuckDB-WASM's apache-arrow dependency is always resolved to the latest release (`dist/npm.js`). Bare imports resolve from the locked `node_modules` and are bundled (`dist/resolvers.js`). **Strong** (source code).
- Framework's documentation says remote imports are not self-hosted and that DuckDB extensions not named in the config can load at runtime (https://observablehq.github.io/framework/imports and https://observablehq.github.io/framework/lib/duckdb, cited by the second review, not re-fetched). The source agrees: an import written as a full URL passes through unchanged (`dist/resolvers.js`); the json and parquet extensions are self-hosted by default and others only when listed in the config (`dist/config.js`), and listed extensions are downloaded from `extensions.duckdb.org` into the cache under `_duckdb` (`dist/duckdb.js`). So "every browser library is copied into the site" holds only for npm imports and configured extensions. **Strong.**
- The same source pins DuckDB-WASM 1.29.0 with DuckDB 1.1.1 extensions (`dist/duckdb.js`), and the command-line tool sends anonymous telemetry unless `OBSERVABLE_TELEMETRY_DISABLE` is set (`dist/telemetry.js`). **Strong** (source code).
- Notebook Kit is "a command-line tool for building static sites from Observable Notebooks", part of the Notebooks 2.0 technology preview, ISC-licensed (https://github.com/observablehq/notebook-kit, as of 2026-10). Its documentation pages returned HTTP 429 on 2026-10-03, so its DuckDB support was not confirmed. **Moderate.**
- Framework's maintainer recommended in March 2026 that Framework users migrate to Notebook Kit (https://github.com/observablehq/framework/discussions/2046, cited by the third review, not re-fetched). This is recorded as a maintenance risk for Framework; the evidence does not show that Notebook Kit meets this site's requirements. **Moderate.**

**Best practices.** Write dashboard pages with SQL blocks that select and filter small precomputed Parquet files; pin every browser import to an exact version and name every DuckDB extension in the config; set `OBSERVABLE_TELEMETRY_DISABLE=true` in the Makefile; keep story text in the shared story files and pull them in with one page loader per page.

**Pitfalls.** A browser engine reading `.duckdb` files is bounded by DuckDB's storage compatibility: newer versions read older files, but forward compatibility is "best effort" (https://duckdb.org/docs/current/internals/storage.html, as of 2026-10). Framework's DuckDB 1.1.1 cannot be relied on to open a file written by the pinned DuckDB 1.5.5, so the site reads Parquet only. A fresh clone's first build must reach the npm registry and jsDelivr, which the agents' sandbox and CI may or may not allow, and two clean builds can pick different library versions; importing every library by bare name from `node_modules` avoids both at the cost of the built-in SQL blocks and DuckDB client. A tool in maintenance mode, whose maintainer now points users to Notebook Kit, may stop working with a future Node release, though a site already built keeps working.

**Verdict: recommended**, on two conditions: the project owner approves it as an npm dependency, and a spike confirms that it builds in the agents' sandbox and in CI, that the site reproduces from an empty download cache after upstream releases change, with every browser import pinned through `node_modules` and the lockfile or listed as unpinnable, and that every built page loads with networking disabled (section 7). Notebook Kit is rejected because it is a preview.

### 2.4 marimo — rejected as the site tool
**In plain terms.** marimo is a Python notebook that can be exported as a web page running Python in the browser. It is excellent for letting a technical reader edit and rerun SQL, but a set of notebooks is not a narrative website, and browser-side Python is slow to start for a 30-second first impression.

**The evidence.**
- Releases 0.25.0 (2026-09-23) and 0.25.1 (2026-10-01) (https://github.com/marimo-team/marimo/releases, as of 2026-10). CoreWeave announced a definitive agreement to buy Marimo Inc. on 2025-10-30 and said the notebook stays open source under a permissive licence (Apache 2.0) (https://www.businesswire.com/news/home/20251030044722/en/CoreWeave-Acquires-Marimo-to-Unify-the-Generative-AI-Developer-Workflow, 2025-10-30). **Strong.**
- WebAssembly notebooks run "entirely in the browser" with duckdb supported, a 2 GB memory limit, and data placed in a `public/` folder (https://docs.marimo.io/guides/wasm/, as of 2026-10). **Strong.**
- SQL cells use DuckDB by default (https://docs.marimo.io/guides/working_with_data/sql/, as of 2026-10). `mo.ui.chat` supports OpenAI-compatible endpoints, Anthropic and others, and needs an API key (https://docs.marimo.io/api/inputs/chat/, as of 2026-10). **Strong.**
- In 2026, WebAssembly exports began showing the last saved output while the in-browser Python loads (https://marimo.io/blog/newsletter-25, as of 2026-10). **Moderate.**

**Verdict: rejected as the site tool; a candidate for a later "query it yourself" notebook.** It is lockable in `uv.lock` and Python-native, which suits MetricFlow, but it would be a second dependency decision.

### 2.5 Rill — rejected
**In plain terms.** Rill is a fast local dashboard tool with DuckDB inside. It has no narrative pages, runs as a local server, and keeps its own metric definitions.

**The evidence.**
- Apache-2.0; installed with `curl https://rill.sh | sh` (https://github.com/rilldata/rill, as of 2026-10). **Strong.**
- Release 0.90 added Canvas map components, an MCP server for all projects (MCP, the Model Context Protocol, lets AI clients call tools), and embedded DuckDB 1.5.5 (https://docs.rilldata.com/notes, as of 2026-10). Dashboards are Explore views and Canvas layouts built on metrics views (https://docs.rilldata.com/developers/build/dashboards, as of 2026-10). Rill Developer is "a local application" started with `rill start`; AI Chat is described as a Rill Cloud feature (https://docs.rilldata.com/, as of 2026-10). **Moderate.**

**Verdict: rejected.** It is strong on dashboards, but it has no story pages and no static build, and its metrics views would duplicate the catalog.

### 2.6 Streamlit, Dash and Vizro — rejected
**In plain terms.** These build Python web apps. A reader sees nothing until someone runs the app.

**The evidence.** Streamlit: "Streamlit apps have a client-server structure. The Python backend of your app is the server" (https://docs.streamlit.io/develop/concepts/architecture/architecture, as of 2026-10); 1.65.0 on 2026-10-02, Apache 2.0 (https://pypi.org/project/streamlit/). Vizro builds on "Plotly, Dash, and Pydantic", is Apache 2.0, and its Vizro-AI is "no longer actively developed" in favour of Vizro-MCP (https://github.com/mckinsey/vizro, as of 2026-10). Dash runs on Flask and is MIT-licensed (https://github.com/plotly/dash, as of 2026-10). **Strong** for Streamlit and Vizro; **moderate** for Dash (search summary only).

**Verdict: rejected.** No static build, so the site would not open without a running process.

### 2.7 Metabase, Superset, Lightdash and Shaper — rejected
**In plain terms.** These are full BI servers. They suit a team, not a showcase a stranger opens on a laptop.

**The evidence.**
- Metabase's open-source edition is AGPL (https://github.com/metabase/metabase, as of 2026-10). DuckDB arrives through a community driver JAR maintained by MotherDuck; custom drivers are not supported on Metabase Cloud (https://github.com/motherduckdb/metabase_duckdb_driver, as of 2026-10). **Strong.**
- Superset reaches DuckDB through `duckdb-engine`, and an open report says it "doesn't work on Superset 5" (https://github.com/apache/superset/issues/35672, as of 2026-10). **Moderate.**
- Lightdash is MIT-licensed and needs a Postgres metadata database when self-hosted. It connects to DuckDB only through MotherDuck or DuckLake, not a local file (https://docs.lightdash.com/integrations/connect-project, as of 2026-10). **Moderate.**
- Shaper defines dashboards in DuckDB SQL, runs from Docker and is MPL-2.0 (https://github.com/taleshape-com/shaper, as of 2026-10). **Moderate.**

**Verdict: rejected.** Each needs Docker, Java or Postgres, and none writes a narrative well.

### 2.8 Eleventy — fallback
**In plain terms.** Eleventy is a general static-site generator that runs on Node, which the repo already has. It turns markdown into pages well, but it knows nothing about data or charts.

**The evidence.**
- Eleventy renders markdown and other templates to a static site (https://www.11ty.dev/, cited by the review). `@11ty/eleventy` 3.1.6 was published 2026-06-02 and is MIT-licensed, with 33 direct npm dependencies (npm registry, read 2026-10-03). Its default configuration runs markdown through Liquid, so a page can include another file (`src/defaultConfig.js`, `markdownTemplateEngine: "liquid"`). **Strong.**
- Browser DuckDB-WASM can read Parquet (https://duckdb.org/docs/current/clients/wasm/data_ingestion, cited by the review). **Strong.**

**Verdict: fallback.** **Gain:** no new binary; every build-time and browser library locked in `package-lock.json`; actively developed; native includes; and nothing loads from the network unless a page is written to. **Cost:** no built-in chart, input or data layer, so a shared DuckDB-WASM loader and every one of the v1 dashboards are hand-written JavaScript, and DuckDB-WASM's extension files may need copying in by hand. It is adopted if Framework fails its spike, under the same two acceptance tests. No prototype was built.

## 3. Needs that cut across tools

### 3.1 Direct querying for a technical reader
**In plain terms.** The deep-dive reader must query the warehouse in DuckDB. That needs DuckDB, which the repo already pins, plus clear instructions.

**The evidence.** The DuckDB UI "adds a user interface for your local DuckDB instance", is "built and maintained by MotherDuck", and starts with `duckdb -ui` or `CALL start_ui();` from any client. It fetches its files from `https://ui.duckdb.org`, and "by default … your queries and data never leave your computer" (https://duckdb.org/docs/current/core_extensions/ui.html, as of 2026-10). **Strong.**

**Recommendation.** A "Query the warehouse" page and README section give read-only commands through the pinned `duckdb` package, and offer the DuckDB UI as an optional extra. **Gain:** no new dependency, and it matches the roadmap's deep-dive wording. **Cost:** the DuckDB UI needs a network connection and is maintained by a vendor; the plain commands do not. An in-page query box over the Parquet marts is possible in Framework, but untested (inference).

### 3.2 A path to a semantic layer
**In plain terms.** A semantic layer stores each metric's definition once, so every chart computes it the same way.

**The evidence.** dbt Labs relicensed MetricFlow under Apache 2.0 on 2025-10-14 (https://www.getdbt.com/blog/open-source-metricflow-governed-metrics). The repo's own test found that MetricFlow works on the pinned stack, but its parse crashes inside the agents' sandbox (`docs/ai-dlc/reports/data-team-practices--findings.md`, section 2.6). Evidence Core and Rill each define metrics in their own YAML (sections 2.1 and 2.5). **Strong.**

**Recommendation.** Keep the catalog as the only definition. When the governed-metrics bet lands, a `make` step uses MetricFlow to write metric tables, and the site reads them like any mart. **Gain:** no duplicate definitions, and the approach works with any static tool. **Cost:** readers cannot ask for an arbitrary metric breakdown at view time.

### 3.3 A path to an AI chat
**In plain terms.** A chat that answers questions about the business needs a language model. A static website cannot hide the key that pays for one.

**The evidence.** marimo's chat element needs an API key (section 2.4). Rill's AI Chat is a cloud feature (section 2.5). Evidence's agent is part of the hosted Studio (https://docs.evidence.dev/, as of 2026-10). That no static site can keep a secret is inference, but it is standard web practice. **Moderate.**

**Recommendation.** Treat the chat as a separate local service in the roadmap's LATER bet (governed metrics, then an AI chat), reading the governed metrics. The site links to it when it exists. **Gain:** the tool choice does not block or shape the chat. **Cost:** the chat will need its own small server and its own dependency decision.

### 3.4 Every published business result stays tied to the marts and to the game
**In plain terms.** The roadmap's guardrail requires every number the site, README or a dashboard shows to be tied to an in-game source by a dbt test, with a mismatch failing CI (roadmap, North-star outcome, "the numbers match the game"). A mart can pass its schema tests while its figure disagrees with the game, so each published figure needs its own reconciliation test. Two more gaps remain between a tested mart and a reader's screen: the Parquet copy the site serves, and any calculation made after it, in browser SQL, chart code or README prose. Framework permits SQL results to be transformed in chart JavaScript (https://observablehq.github.io/framework/sql, cited by the second and third reviews), so a wrong chart calculation would pass every dbt test and every export check.

**Recommendation.** Five rules, all checked inside `make check`.
- **The rule's scope.** It covers business results, meaning figures measured from the parks' data (visitors, money, ratings, units sold, and anything computed from them), in charts, tables and the README. Explanatory numbers in story text, such as game-calendar constants, rules and measured plugin timings, are not mart columns; they pass when their sentence cites a source.
- **Each published business result is reconciled to the game.** A committed mapping gives each one its mart query, its in-game source (for example a monthly-statement line, cash, the park rating or a ride's ratings as the plugin recorded them) and the dbt reconciliation test that fails `make check` when the modeled value drifts from that source. A result computed from several values names the source and test of each input. README results are generated from the mapped queries, and dashboard figures are asserted against them.
- **Charts show mart rows as delivered.** Each chart is a declarative spec naming its mart relation, the columns it plots, the input that filters it and its title key; one shared chart function runs the spec's select-and-filter query and passes the rows to Plot unchanged. A source check rejects page and chart code that calls Plot directly, uses a Plot transform that groups, bins or reduces, maps over data rows, or writes its own query, and a Node test asserts that the shared function's marks carry the mart rows unchanged. **Gain:** no arithmetic can enter between the mart and the screen, with no new dependency. **Cost:** a spec format and one shared function, and a chart can show only what a spec can name.
- **Exports match their marts.** After dbt builds the marts from the committed sample, a script rebuilds every export from its mart and compares it with the copy the site serves, by row count and by a hash of the sorted rows. Exports come only from a short allowlist of approved mart relations.
- **No unmapped result.** A business result in a chart, table or the README with no mapping entry fails the publication check.

**Gain:** a drift from the game, a wrong chart calculation or a wrong README result fails the gate, not only a changed export. **Cost:** a mapping file, reconciliation tests per published result, the chart-spec format, two scripts, a few seconds of gate time, and marts that carry every displayed figure precomputed. **Build acceptance (mutation tests):** changing one value in a served export with its mart intact fails `make check`; adding an export of a relation not on the allowlist fails it; changing a published result's in-game source or its modeled value so that the two drift fails it; adding a calculation in chart code with the mart, export and mapping unchanged fails it; changing one README result with marts unchanged fails it; and a cited game-calendar constant passes while an unmapped business result fails (ADR 0015, "Build acceptance tests").

## 4. One source of text for the README and the site

**In plain terms.** The README and the site must tell the same story without being edited twice. GitHub cannot pull one file into another, so the README is generated from the same story files the site uses. The site is checked at its sources, not by comparing rendered pages, because rendered pages are both too strict and too loose.

**The evidence.**
- GitHub's README guidance covers what a README holds and relative links, but offers no include mechanism (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes, as of 2026-10). A request for markdown includes opened in 2015 never received a plan before its tracker was archived in 2021 (https://github.com/isaacs/github/issues/471). **Strong.**
- Framework has page loaders (section 2.3), Quarto has includes and gfm output (section 2.2), Eleventy has Liquid includes (section 2.8), and Evidence has partials (section 2.1). **Strong.**
- Generators exist that write content between markers in a file, such as cog, which is MIT-licensed (https://cog.readthedocs.io/, as of 2026-10). Each is a new dependency. **Moderate.**
- Checking only the generated README leaves the site unchecked: a page can drop its include, or wrap it in contradictory prose, and the README check still passes (first review, finding 6). **Strong** (follows from the design).
- Comparing built pages with the story text fails both ways. Framework's page loaders emit markdown that is then rendered to HTML, so valid formatting changes the text a literal comparison sees; and its SQL results and charts render in the browser, so an HTML check cannot see a chart title typed into page code (https://observablehq.github.io/framework/page-loaders and https://observablehq.github.io/framework/sql, cited by the second review, not re-fetched). **Moderate.**

| Option | How it works | Fits | Gain | Cost |
|---|---|---|---|---|
| A. The site tool renders the README | `README.qmd` with `format: gfm` includes the story files | Quarto only | Native; no script | Quarto joins every README change and the gate; pandoc reformats the markdown |
| B. The site includes the README | Site pages pull in sections cut from `README.md` | Any tool with includes | README stays hand-written | Section boundaries in the README become a hidden interface |
| **C. Story files, a generated README, and source checks (recommended)** | Story files; a stdlib script generates the README and checks it byte for byte; a source check asserts each story file is included exactly once through the site tool's include mechanism; titles and annotations come from the story files or the catalog | Any tool with includes or page loaders | Both outputs checked at the source; no rendered-HTML comparison; no dependency; survives a tool change | About 150 lines plus tests |
| D. A third-party generator | cog, markdown-magic, markdown-include | Any | Ready-made | A new dependency for a job the standard library does |

**Recommendation: option C**, with these rules.
- **The story files.** Five markdown files under `docs/showcase/story/`: the game, the company timeline, the analytics strategy, the stack, and "How this was built". Story text lives only there. Drafts exist (section 8).
- **The README.** A standard-library script generates `README.md` from the story files, followed by the "Run it yourself" section of `docs/showcase/story/README.md`. Today's `README.md` run instructions move into that section unchanged when the script is built, so it becomes their only source. `make check` regenerates the README and compares it byte for byte, failing on any difference, and fails when a `make` target named in that section does not exist.
- **The site, checked at its sources.** Each site page pulls in its story file through the site tool's include mechanism: in Framework, a page loader that reads the file; in Eleventy, a Liquid include; in Quarto, an include shortcode. Each such page (a wrapper) contains only the include directive: in Framework a one-line page loader, in Eleventy one Liquid include. A source check reads the site's page sources and fails on any other text in a wrapper, and unless each story file is included exactly once across all pages. Dashboard pages hold only chart specs. No rendered HTML is compared.
- **Chart titles and annotations.** They are taken from the story files or the metric catalog, never typed into page code, and the source check fails on a title or annotation written as text in a page.
- **Links.** Every link in a story file is root-relative: it starts with `/`, meaning the repo root, which GitHub resolves from the repo root in the README (GitHub's relative-link guidance, not re-fetched in this pass). The site build copies or maps each linked document to the same path, and the check resolves every link in both outputs and fails when either target is missing.
- **Build acceptance criteria (mutation tests).** A contradictory paragraph added to a wrapper that keeps its single include fails `make check`; a chart title changed in page code fails it; a page that omits its story file's include fails it; editing the README's run instructions without their source fails it; a valid formatted paragraph in a story file (bold text, a list) passes; and a valid root-relative document link passes.

## 5. What the first screen must say

**In plain terms.** Readers decide within seconds whether to keep going. The top of the page should give the conclusion first, in plain words, with one picture.

**The evidence.**
- "The first 10 seconds of the page visit are critical"; pages must "communicate your value proposition within 10 seconds"; visitors who stay about 30 seconds tend to stay much longer (Jakob Nielsen, https://www.nngroup.com/articles/how-long-do-users-stay-on-web-pages/, 2011-09-11). **Strong**, though dated.
- The inverted pyramid puts "the most important information … first", so a reader can stop at any point and keep the main point (Amy Schade, https://www.nngroup.com/articles/inverted-pyramid/, 2018-02-11). **Strong.**
- A "Big Idea" is one complete sentence that states a point of view and what is at stake (storytelling with data, after Nancy Duarte; https://community.storytellingwithdata.com/exercises/whats-the-big-idea, as of 2026-10). **Moderate.**
- A README should say what the project does, why it is useful and how to start (GitHub guidance, above). **Strong.**
- Recruiters skimmed résumés for an average of 7.4 seconds and favoured simple layouts with clear headings (TheLadders eye-tracking study, https://www.theladders.com/career-advice/you-only-get-6-seconds-of-fame-make-it-count, 2018). This measures résumés, not project sites. **Moderate, by analogy.**

**What the top of the page must carry**, in this order:
1. A one-sentence big idea: a simulated theme-park company, run on real game events, with its analytics built as a data team would.
2. One line on RollerCoaster Tycoon, the game in which players build and run theme parks.
3. One line on the company: several parks on one company calendar, with free entry and income from rides and stalls, labelled a one-person simulation.
4. One headline chart whose title states its takeaway, with "rehearsal data", its sample (parks), its unit and its clock visible.
5. Links to the four sections (the game, the company timeline, the analytics strategy, the stack) and one link to "How this was built".

Stack detail, verification and process documents sit below or one click away, within the 5-minute read. The same order opens the README. The first screen is only the start: the full list of v1 requirements the site carries, each with its acceptance check, is in ADR 0015.

## 6. Where sources disagree
- **Is Evidence Core static, and can it read local files?** Its front page says it builds a static site, and its README says the same. Its self-hosting page describes a Docker production server with Basic Auth, and its flat-file connector is documented under Studio's managed warehouse. Unresolved; these are the re-check conditions in section 2.1.
- **Evidence's open-source commitment.** In 2025-06 Evidence said it would keep developing the open-source framework and make it compatible with Studio (https://evidence.dev/blog/evidence-studio). It did so by replacing that framework with Core, not by updating it. Both statements are true, but the 2026-09-27 choice assumed the old framework.
- **Is Framework alive?** Its maintainer says it continues to work and be supported, and a patch shipped in 2026-03; new development has moved to Notebooks 2.0. Both are true. For a static site whose built output does not depend on the tool afterwards, supported-but-not-developed is an acceptable risk; for a long-lived product it would not be.
- **Quarto against Framework for dashboards.** Community write-ups call dashboards Framework's core purpose and an add-on in Quarto (search summary of https://www.appsilon.com/post/observable-framework-data-science-dashboards, as of 2026-10), but Quarto documents a client-side dashboard format of its own (https://quarto.org/docs/dashboards/interactivity/). The gap is therefore narrower than the write-ups suggest: Framework's edge is its built-in DuckDB client and SQL blocks, and, on the locked route, its lockable npm package. Every v1 dashboard group needs charts, inputs and a browser DuckDB, and the story is five plain files, so Framework still fits better (section 1.1).
- **Does Framework's build make the site self-contained?** Its build copies imported npm libraries into the site, but its documentation excludes remote imports from that, and an extension left out of the DuckDB config can load when a page runs. Both are true; the offline page-load test inspects every built page with networking disabled.

## 7. Gaps and thin evidence
- **Untested, because nothing could be installed:** whether Framework builds inside the agents' sandbox and in CI (a fresh build must reach the npm registry and jsDelivr), whether the site reproduces from an empty download cache after upstream releases change, how large its download cache is, whether the built site loads with networking disabled, install sizes for every candidate, and how long a site build adds to the roughly 10.5-minute gate. These form the proposed spike: build a two-page site with one chart over a mart Parquet file, in the sandbox and in CI; record the resolved version of every browser import, then rebuild from a fresh clone with an empty download cache after an imported library or one of its dependencies has published a newer release, and compare the served files; then load every built page with networking disabled, record every network request, and reject any unintended remote import or DuckDB extension load.
- **Unverified:** Evidence Core reading local Parquet or a DuckDB file without Studio; a reader-facing SQL console in either Evidence line; Notebook Kit's DuckDB support (its documentation was rate-limited).
- **Not re-fetched in the review passes:** Quarto's external-host page, issue 1412 and dashboard page; Framework's discussion 2046 on Notebook Kit; Evidence's warehouse and CLI connection pages; Eleventy's front page; and Framework's import, DuckDB, SQL and page-loader pages. These rest on the reviews' links, and Framework's also on its source code.
- **Legacy Evidence documentation:** legacy-docs.evidence.dev loads over HTTPS (checked 2026-10-03 through the web client; certificate dates not inspected). The earlier expired-certificate claim was made against a different host name, `legacy.docs.evidence.dev`, and stays withdrawn.
- **Thin:** no source studies how hiring reviewers read a project website. Section 5 rests on general web-reading research and a résumé study.
- **Not researched, by design:** hosting, which waits for the public-repo conversation, and the visual design of the site.

## 8. What changes
- ADR 0015 records the proposal and the v1 requirements the site must carry. Its status is proposed until the project owner signs off on the dependency.
- **The fallback changes from Quarto to Eleventy** (section 1.1); the recommendation stays Observable Framework.
- **Narrative drafts are written** as plain markdown in `docs/showcase/story/`, one file per story section, for the project owner's review: the game; the company timeline; the analytics strategy; the stack; and "How this was built" (AI agents wrote most code and documents, what the project owner decided, how blind reviewers checked the work, and two real examples of agent output that review corrected, each naming its ledger row and the change it caused). Each draft has at most 200 words of body, about a 30-second read. Once approved they become the story files unchanged.

- Not changed here, because only NEXT 15 may be edited in this change: item 3e (the dashboard line, folded into the website) still names Evidence as the 2026-09-27 default. It should be updated when the ADR is accepted.
