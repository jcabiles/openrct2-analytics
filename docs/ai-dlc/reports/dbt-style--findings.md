# dbt Labs style compared with this repository

## Bottom line

dbt Labs’ current guides and this repository agree on staging, intermediate, and marts as useful layers, on cleaning source data in staging, and on documenting and testing model keys. [dbt structure guide](https://docs.getdbt.com/best-practices/how-we-structure/1-guide-overview) (read 2026-10-03); [dbt model style guide](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (read 2026-10-03). The main deliberate differences are this repository’s event and grain based names, full rebuilds of tables at every layer, game-date fact keys, and distinct tests for identities and hypotheses; its accepted [ADR 0016](../../../docs/adr/0016-dbt-design.md) should govern those choices. The three existing staging models are still skeleton views with direct `select` statements and inline money conversions, so several local rules describe the planned rework rather than current code. [dbt_project.yml](../../../dbt_project.yml); [stg_finance_monthly.sql](../../../models/staging/stg_finance_monthly.sql). Adopt the low-cost readability rules now; add SQLFluff to the gate only after the project owner approves its new dependencies and the existing SQL has been formatted. [dbt SQL style guide](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql) (read 2026-10-03); [SQLFluff dbt templater](https://docs.sqlfluff.com/en/stable/configuration/templating/dbt.html) (read 2026-10-03).

**Scope and terminology.** A *common table expression* (CTE) is a named query within a SQL statement. A dbt *model* is a query that dbt builds as a table or view. *Staging* cleans inputs, *intermediate* models prepare transformations, and *marts* serve business use. “Matches,” “differs,” and “silent” below compare the guidance with current files; where a local rule is planned but not implemented, the cell says so. Local files were read on 2026-10-03.

## Conventions and current practice

| Topic | dbt Labs convention | Primary source and date read | This repository |
|---|---|---|---|
| SQL case, commas, indentation, length | Lowercase keywords, functions, and fields; trailing commas; four-space indentation; SQL lines at most 80 characters. | [SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql) (2026-10-03) | **Mixed.** The three [staging SQL files](../../../models/staging/stg_park_daily.sql) use lowercase, trailing commas, and four spaces. Long money expressions exceed 80 characters; across the three SQL and three YAML files, 137 lines exceed 80 characters. [stg_finance_monthly.sql](../../../models/staging/stg_finance_monthly.sql); [stg_park_daily.yml](../../../models/staging/stg_park_daily.yml). |
| Aliasing and joins | Write `as` for field and table aliases. Qualify columns when joining, spell out join types, avoid terse table aliases and `right join`, and prefer `union all` unless deduplication is intended. | [SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql) (2026-10-03) | **Matches where applicable; otherwise silent.** Existing aliases use `as`; [local rules](../../../.claude/rules/dbt.md) prohibit staging joins. No intermediate or mart joins exist yet. |
| Aggregation and grouping | Put fields before aggregates and window functions; aggregate before a join when practical; prefer positional `group by 1, 2` and `order by 1, 2`. | [SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql) (2026-10-03) | **Silent in code.** Staging has no aggregation. The [module map](../../../docs/CONVENTIONS.md) puts grain changes in intermediate models. Positional grouping has no local rule. |
| CTE structure | Place `ref()` calls in import CTEs at the top, named for their inputs. Give each later CTE one clear task where practical; finish with `select *` from the final CTE. The staging example uses `source`, then `renamed`. | [SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql); [staging guide](https://docs.getdbt.com/best-practices/how-we-structure/2-staging) (both 2026-10-03) | **Differs.** All three [staging models](../../../models/staging/stg_sessions.sql) currently use one direct `select` with no CTE. |
| Staging names and folders | Usually `stg_[source]__[plural_entity]`, grouped by source system; a single-source project may omit the source prefix. Keep staging near a one-to-one mapping with source tables. | [staging guide](https://docs.getdbt.com/best-practices/how-we-structure/2-staging); [model style](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (both 2026-10-03) | **Differs by design.** [Section 3](../../../docs/CONVENTIONS.md) specifies `stg_<event_type>` and one model per event contract, plus `stg_envelope` across event types. The existing `stg_park_daily`, `stg_finance_monthly`, and `stg_sessions` names await that rework. |
| Intermediate names and folders | Use `int_` names that say what an entity is being *done to*, such as `int_order_items_summed_to_orders`. Group by business concern when the project warrants subfolders. | [intermediate guide](https://docs.getdbt.com/best-practices/how-we-structure/3-intermediate) (2026-10-03) | **Partly matches in intent; no models yet.** [Section 3](../../../docs/CONVENTIONS.md) reserves `int_<grain>__<step>` for save lineage, company dates, counter changes, keys, and business deduplication. |
| Mart names and folders | Name marts for business entities, commonly plural; group by business concern if useful. The example’s marts are wide entity tables, with different advice where the Semantic Layer is used. | [marts guide](https://docs.getdbt.com/best-practices/how-we-structure/4-marts) (2026-10-03) | **Differs by design; no marts yet.** [ADR 0016](../../../docs/adr/0016-dbt-design.md) requires `dim_`, `fct_`, and `obt_` tables. Site-facing `obt_` tables read only the star. Marts await confirmation of the requirements brief. |
| Materialization | Typically stage as views; start intermediate models as ephemeral or isolated views; use tables or incremental models for marts as performance warrants. Jaffle Shop configures staging views and mart tables. | [staging](https://docs.getdbt.com/best-practices/how-we-structure/2-staging); [intermediate](https://docs.getdbt.com/best-practices/how-we-structure/3-intermediate); [marts](https://docs.getdbt.com/best-practices/how-we-structure/4-marts); [Jaffle Shop project config](https://github.com/dbt-labs/jaffle-shop/blob/main/dbt_project.yml) (all 2026-10-03) | **Differs by accepted rule, with implementation pending.** [CONVENTIONS](../../../docs/CONVENTIONS.md) requires full-rebuild tables in layer schemas and no incremental models. [dbt_project.yml](../../../dbt_project.yml) has no layer configs yet, so the existing skeleton models remain default views. |
| Sources and references | Use `source()` at the staging boundary and `ref()` for upstream dbt models; the staging guide generally uses one staging model per source table. | [staging guide](https://docs.getdbt.com/best-practices/how-we-structure/2-staging); [workflow best practices](https://docs.getdbt.com/best-practices/best-practice-workflows) (both 2026-10-03) | **Matches today, with a planned exception.** The three [staging SQL files](../../../models/staging/stg_park_daily.sql) use `source('landing', ...)`, declared in [_sources.yml](../../../models/staging/_sources.yml). No downstream `ref()` exists yet. Planned `stg_envelope` reads several event types. |
| Tests by layer | Test keys for uniqueness and non-nullness; use reusable generic data tests for common assertions, singular SQL data tests for one-off assertions, and unit tests with fixed inputs for complex SQL logic. Unit test YAML belongs beside models; data test SQL belongs under `test-paths`. | [workflows](https://docs.getdbt.com/best-practices/best-practice-workflows); [unit tests](https://docs.getdbt.com/docs/build/unit-tests); [data tests](https://docs.getdbt.com/docs/build/data-tests) (all 2026-10-03) | **Partly matches.** Existing [model YAML](../../../models/staging/stg_sessions.yml) contains key tests and unit tests; [tests/dbt](../../../tests/dbt/assert_stg_park_daily_passes_weather_through.sql) contains singular tests. Intermediate unit tests, mart contracts, exact sample counts, and identity versus hypothesis tests are specified in [CONVENTIONS](../../../docs/CONVENTIONS.md) but not built. |
| YAML and documentation | Use two-space YAML indentation and roughly 80-character lines; describe models and columns in YAML. Enforced model contracts specify every column’s name and data type. | [YAML style](https://docs.getdbt.com/best-practices/how-we-style/5-how-we-style-our-yaml); [model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts) (both 2026-10-03) | **Mixed.** [Staging YAML](../../../models/staging/stg_finance_monthly.yml) uses two-space indentation and detailed descriptions but has long descriptions and SQL fixtures. Every existing model description states “one row per …”; the local [rule](../../../docs/CONVENTIONS.md) also requires a key. Mart contracts are planned. |
| Macros, Jinja, and Python | Use spaces inside Jinja delimiters and four spaces within Jinja blocks. Put reusable transformations in macros where useful. For Python, dbt Labs recommends Black formatting and Ruff linting. | [Jinja style](https://docs.getdbt.com/best-practices/how-we-style/4-how-we-style-our-jinja); [staging example](https://docs.getdbt.com/best-practices/how-we-structure/2-staging); [Python style](https://docs.getdbt.com/best-practices/how-we-style/3-how-we-style-our-python) (all 2026-10-03) | **Mixed.** Existing `source()` calls lack spaces inside `{{ ... }}`. There are no dbt Python models; the repository already uses Ruff for its Python code. |
| SQL linting | Use SQLFluff with project-specific rules. Its dbt templater renders dbt macros more faithfully than the simpler Jinja templater, at a cost in speed and setup. Jaffle Shop has a SQLFluff config, although its current `dbt-cloud` templater and Snowflake dialect are specific to that example. | [SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql); [SQLFluff templater](https://docs.sqlfluff.com/en/stable/configuration/templating/dbt.html); [Jaffle Shop SQLFluff config](https://github.com/dbt-labs/jaffle-shop/blob/main/.sqlfluff) (all 2026-10-03) | **Differs.** [CONVENTIONS](../../../docs/CONVENTIONS.md) has a `make check` gate but no SQLFluff step or SQL style rule; [pyproject.toml](../../../pyproject.toml) has no SQLFluff dependency. |

## Where the sources changed or disagree

The public [corporate `dbt_style_guide.md`](https://raw.githubusercontent.com/dbt-labs/corp/main/dbt_style_guide.md) is still retrievable, but its contents now direct readers to the expanded Developer Hub guide; the [corporate repository](https://github.com/dbt-labs/corp) is archived. Both were read on 2026-10-03. The [current style overview](https://docs.getdbt.com/best-practices/how-we-style/0-how-we-style-our-dbt-projects) explicitly presents its choices as suggestions and acknowledges differing preferences within dbt Labs, so the relocated guide does not override a deliberate local rule. (Read 2026-10-03.)

The guides also describe choices for different project sizes: the [intermediate guide](https://docs.getdbt.com/best-practices/how-we-structure/3-intermediate) explains when to add that layer, while [Jaffle Shop’s current model tree](https://github.com/dbt-labs/jaffle-shop/tree/main/models) contains staging and marts only. Jaffle Shop’s [README](https://github.com/dbt-labs/jaffle-shop) says its current main branch requires dbt v2.0.0 or higher; it is a style example, not a dbt 1.11 compatibility test. (All read 2026-10-03.) The documentation pages opened for [contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts), [unit tests](https://docs.getdbt.com/docs/build/unit-tests), [data tests](https://docs.getdbt.com/docs/build/data-tests), and [severity](https://docs.getdbt.com/reference/resource-configs/severity) were the live pages, which may include later-version material. The repository’s [ADR 0016](../../../docs/adr/0016-dbt-design.md) records probes on its pinned dbt Core 1.11.15 and dbt-duckdb 1.11.0 stack; those local probes are the stronger evidence for its particular contract and test settings. (Documentation read 2026-10-03.)

## SQLFluff decision

**Propose adding SQLFluff, subject to the project owner’s dependency approval.** It would make the chosen SQL case, spacing, commas, aliases, and line length checkable rather than relying on review alone; dbt Labs recommends it for that purpose. [dbt SQL style](https://docs.getdbt.com/best-practices/how-we-style/2-how-we-style-our-sql) (read 2026-10-03). The cost is two Python dependencies (`sqlfluff` and `sqlfluff-templater-dbt`), locked-version maintenance, slower dbt rendering, and an initial cleanup. SQLFluff says its dbt templater may need database access when a macro queries the database during compilation. [SQLFluff dbt templater](https://docs.sqlfluff.com/en/stable/configuration/templating/dbt.html) (read 2026-10-03). Do not copy Jaffle Shop’s `dbt-cloud` templater or Snowflake dialect into this DuckDB project. [Jaffle Shop config](https://github.com/dbt-labs/jaffle-shop/blob/main/.sqlfluff) (read 2026-10-03); [profiles.yml](../../../profiles.yml).

Proposed `.sqlfluff` settings, to validate against the approved and locked SQLFluff version before adding them to `make check`:

    [sqlfluff]
    dialect = duckdb
    templater = dbt
    encoding = utf-8
    max_line_length = 80

    [sqlfluff:templater:dbt]
    project_dir = .
    profiles_dir = .
    target = dev
    dbt_skip_compilation_error = False

    [sqlfluff:indentation]
    indent_unit = space
    tab_space_size = 4

    [sqlfluff:layout:type:comma]
    line_position = trailing

    [sqlfluff:rules:capitalisation.keywords]
    capitalisation_policy = lower

    [sqlfluff:rules:capitalisation.functions]
    capitalisation_policy = lower

    [sqlfluff:rules:aliasing.table]
    aliasing = explicit

    [sqlfluff:rules:aliasing.column]
    aliasing = explicit

Use `.sqlfluffignore` for generated `target/` and any `dbt_packages/` folder; lint model SQL and singular data test SQL, with `sqlfluff lint models tests/dbt` as the proposed gate command. The project has no dbt packages, but the ignore entry prevents generated package SQL from joining the gate if that policy changes. SQLFluff documents the project and profile settings and the dbt templater’s compilation behavior; its [layout documentation](https://docs.sqlfluff.com/en/stable/configuration/layout.html) covers the comma and indentation settings. (Both read 2026-10-03.) Run the proposed command on the existing files and resolve its findings before making it a failing `make check` step. The current repository rule requires project-owner approval for any new dependency. [CONVENTIONS](../../../docs/CONVENTIONS.md).

## Ready-to-paste draft for `docs/CONVENTIONS.md`

### dbt SQL style

- Write SQL keywords and functions in lowercase. Use trailing commas, four spaces for indentation, explicit `as` for aliases, and lines of at most 80 characters where a readable break is possible. Check: SQLFluff after its dependencies are approved and added to `make check`; judgment only until then.
- When a model has several transformation steps, put `source()` and `ref()` inputs in named CTEs first, give each later CTE one clear purpose, and end with a select from the final CTE. A simple, single-source staging pass-through may use one direct select. Check: judgment only.
- Spell out join types, qualify columns read from joined relations, and use descriptive relation names. Staging still has no joins. Check: judgment only, with SQLFluff checking supported syntax rules after approval.
- Keep model YAML beside its SQL. State its key and grain as “one row per …”; describe column units and clocks, and retain the existing column-name suffix rules and their stated exceptions. Check: judgment only.
- Keep the accepted `stg_`, `int_`, `dim_`, `fct_`, and `obt_` naming, full-rebuild tables, staging-only money conversion, game-date fact keys, and identity versus hypothesis test rules. The project’s dbt rules take precedence when dbt Labs examples use different choices. Check: the existing checks named in section 4, plus judgment only for the remaining rules.
