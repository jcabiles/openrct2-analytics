# Spec: hide Sandbox parks from the dashboard's "All parks" figures

**Bottom line.** The company dashboard's "All parks" view will leave Sandbox (throwaway practice) parks out of every figure by default. A switch on each page, in the park filter, puts them back in, and it names each hidden park as `<park name> (first played <Mon D>)`. Nothing is deleted. `make delete-company-data`, with its typed confirmation and its archive-first rule (ADR 0033), stays the only delete path and does not change.
- **The data builder** (`dashboard/data.py`) marks a park as Sandbox when `marts.dim_park.park_number` is null, which is the existing warehouse signal. The default "All parks" totals are summed from each company park's monthly statements. The builder no longer reads the all-park company mart. For the additive fields that `data.py` reads, over the company dates that both marts hold, the totals with Sandbox parks shown equal that mart (D2).
- **The switch** keeps its state only in the page address (`?sandbox=shown`), so no stored state is added. The server passes the parks' names and first-played dates to the page on each load, from the label helper that "Name parks by name, not only by ID" adds.
- **The banner sentence** about a Sandbox park is reworded so that it stays true whether the switch is on or off.
- **An existing warehouse needs one rebuild.** A warehouse built before `park_number` exists makes the dashboard show "Not updated: the rebuild failed" until the player files a play through the launcher, which rebuilds it (R18).
- No dbt model, data contract, Makefile line, delete code or dependency changes. Three tickets build it: the data, then the server and pages, then the docs.

## 2. Decisions the map leaves open

**D1. A park is Sandbox for `data.py` when `marts.dim_park.park_number` is null. No dbt change is needed.**
- `data.py` may read only the `marts` schema (ADR 0054, Decision, "One data file"; map TOP 2). The registry table that the banner reads, `intermediate.int_park_registry__current` (`ingest/dashboard.py:67,113-138`; `_warnings` now returns `(warnings, practice)`), is outside that schema.
- `dim_park.park_number` is null exactly for a Sandbox park. The `numbered` step numbers only the registry rows whose note is distinct from the practice note (`models/marts/dim_park.sql:30-43`, the filter at `:42`), and `final` left-joins it (`:97-99`). ADR 0057 (Decision 1) makes this the rule: "A Sandbox park (registry note equal to the practice note) has no number". The macro and the Python constant are pinned equal by `tests/test_practice_note.py:31` (map TOP 2).
- **Classification covers registered parks only.** `dim_park` is built from the registry (`models/marts/dim_park.sql:12-19`), so the rule applies to registered `dim_park` rows. A registered Sandbox park has a null `park_number`. A registered company park with no kept session still gets a number (`first_starts` is left-joined, nulls last, `:30-43`) and can have a null `park_name`. An unregistered park has no `dim_park` row, and its statements reach the marts with a null company date (`models/intermediate/int_statements__labeled.sql:60-66,104-109`; `int_park_years__registry_mapped.sql:36-66`). The summed query excludes them explicitly by `company_date is not null`, so no unregistered park or unmapped statement enters any scope. `data.py` also counts only parks that `dim_park` lists: the `list_contains($parks, ...)` filter holds the `dim_park` IDs.
- Rejected: a new boolean column on `dim_park`. Gain: a self-describing name. Cost: a model, YAML and unit-test change, plus the built-columns check, all to state a fact that the column already holds. The brief prefers the existing signal "unless a reason forces a dbt change", and none does.
- The banner keeps its own registry read, which PN-R12 owns (PN spec, PN-R12). Both reads come from one registry note through one pinned literal, so they cannot disagree in a coherent build. A test plants both signals and checks that they agree (R2). Gain: no edit to the query PN-T5 owns. Cost: the fact is still read in two places, as it is today. (Changed at build, see ticket SH-T3: the banner's Sandbox set comes from the current data build's parks with `sandbox: true`, one source for the banner, the labels script and the pages; the separate registry read is gone.)

**D2. Every "All parks" total is a sum of `marts.obt_park_month` over the parks in view. `obt_company_month` is no longer read by `data.py`.**
- Today the all-parks months and the month gate both come from `obt_company_month` (`dashboard/data.py:50-53,60-63`). That mart sums every park, Sandbox included, with no park column to filter on (`models/marts/obt_company_month.sql:28,70-93`; map TOP 1).
- **Parity is limited to the additive fields `data.py` reads, over mapped dates.** Every column that `data.py` reads (`_MONTH_COLUMNS`, `data.py:54-59`) is additive in both marts: the statement amounts (revenue lines, cost lines, capital spending, operating profit), `guest_visits` and `operating_days`. Both marts read `fct_park_month` (`obt_company_month.sql:28`, `obt_park_month.sql:30`), and `obt_park_month.company_date` is the statement's company date (`obt_park_month.sql:200`). For those fields, a sum over the parks in view is the company total of those parks, and over every park it equals `obt_company_month` on every company date that both marts hold (proven by R4 on a real dbt build). Not claimed: `company_date` and `company_year` are keys, not sums. `parks_reporting` is a distinct park count and `average_park_rating` and the per-visit and per-day rates pool their inputs (`obt_company_month.sql:70-93,165-188`). The park-only shares and entrance revenue per visit have no company counterpart. `obt_company_month` can also hold a group with a null company date; the summed query leaves it out (D1).
- **Non-additive figures are computed for the scope from summed numerators and denominators, never by averaging park rows.** The month record `data.py` exports holds only the additive fields above plus cash and guests (`data.py:249-267`), and the pages read nothing else from `obt_company_month`: no `parks_reporting`, no `average_park_rating` and no per-visit or per-day rate (`app/executive.js:99-107` reads `profit`, `rev`, `visits` and `cash` sums only). The averages and counts that the pages do show are made from the scope's own rows: the day and ride averages (`_BY_AGE` `avg(...)`, `data.py:162-167`; `operations.js:18` `mean`) run over the scope's kept days, and the sample line's park count is the length of `park_ids` (`shared.js:55`). If a page later needs a per-visit or per-day rate, it is the scope's summed numerator over its summed denominator (for example summed `rev` over summed `visits`), in mart dollars. R17 pins that the month record holds no field outside the additive list.
- One query serves every scope kind: `where list_contains($parks, park_id) and company_date is not null group by company_date`. A one-park scope sums one row per month, which is that row. Gain: the two-kind dictionaries and the `$park` parameter are deleted (one path, not two). Cost: about 15 lines of SQL change in `data.py`, and one extra `group by` per scope build.
- **The month gate is one row per company month.** `_KEPT_DAY` inner-joins `statement_month` to every kept park day (`data.py:64-71`), so a gate that repeated a month once per in-view park would repeat each kept day. The gate is `select distinct company_date as month_start from marts.obt_park_month where list_contains($parks, park_id) and company_date is not null`. A month opens when at least one in-view park closed it (has a statement for it). A month that only a Sandbox park closed is absent from the default view and opens with Sandbox included.
- **Cash and guests in the park follow the in-view parks, not the closing parks.** Neither monthly mart holds them. For a scope, the month's cash is the sum over each in-view park of its last kept USD cash reading in that company month, and the same for guests in the park (`_MONTH_TOTALS`, `data.py:94-102`, which sums each park's `last(... order by company_date)`). A park that did not close the month still adds its last kept reading if it has kept days in it. The monthly marts, in contrast, sum visits and operating days only over parks with a statement (`obt_company_month.sql:55-93`, `obt_park_month.sql:57-69`). The two rules stay different, and R17 pins both.
- Rejected: a new mart that leaves Sandbox parks out. Gain: none that the sum does not give. Cost: a dbt model, exports and checks.
- Money stays in mart dollars. Sums of `decimal(18, 2)` columns are exact. `data.py` still only flips cost signs and rounds (`_number`, `_cost`, `data.py:175-186`; map §5).

**D3. A hidden Sandbox park stays in the park picker, under its name, and keeps its own scope.**
- The pass/fail asks only that the "All parks" figures leave Sandbox parks out. Today a Sandbox park already has its own scope and picker entry when there are several parks (`data.py:373-374`; map §1).
- Gain: a Sandbox park can still be looked at alone, and nothing on the dashboard becomes unreachable. Cost: two same-named Sandbox parks still show identical picker entries (open question Q1).
- The rule for building one scope per park becomes "more than one park, or any Sandbox park". The picker shows "All parks" plus each park under that same rule. Without this, a warehouse holding a single Sandbox park would offer only an empty "All parks" view.

**D4. The switch lives in `shell()` in `app/shared.js`, inside `#parkBox`, and its state lives only in the address query `?sandbox=shown`.**
- `shell()` runs on all five pages and fills `#parkBox`, which every page has (`app/shared.js:59-73`; map §3). The query is already the only page state, applied by reloading the page (`shared.js:43,69`). The roadmap forbids new stored state. `?sandbox=shown` is the only inclusion control: park IDs resolve only from real parks (`DATA.scopes[PARK]` with `PARK` a `parks` ID, `shared.js:43-44,60-69`), and no special park value such as `with_sandbox` is routable.
- The control reuses `chips()` (`shared.js:35`): two buttons with `aria-pressed`, "Left out" and "Included", under a heading "Sandbox parks". Choosing one reloads the page with or without `sandbox=shown`. Gain: no new control type and no new CSS; it uses the existing keyboard and focus handling. Cost: one reload for each switch, and each reload returns keyboard focus to the top of the page. That is a known cost; the project owner judges it in the browser look on the morning list (SHR-10).
- The switch is drawn only in the "All parks" view, and only when at least one park is Sandbox. On a one-park view it would change nothing.

**D5. The banner sentence is reworded so that it is true in both states. The server does not read the query.**
- Today's sentence, `Practice park p2 is included in these figures; ...` (`ingest/dashboard.py:344-348`, built in the banner lines from `Build.practice`, `:104`), becomes false by default (map TOP 3). PN-R12 rewrites it to one sentence per park with a label. The banner is rendered by the server and ignores the query (`dashboard.py:333-358` for the banner, `:360-366` for `Dashboard.page`).
- The new sentence is `Sandbox park <label> is left out of the All parks figures unless Sandbox parks are included; remove it with make delete-company-data PARK=<id>.` It is true with the switch on or off, and on a one-park view. Gain: `do_GET` and the build caching stay as they are. Cost: the sentence speaks of the default, not the current state; the switch note states the current state (R8).
- "Sandbox" replaces "Practice", so that the banner, the switch and the launcher (which shows practice as Sandbox, `AGENTS.md`, `make register-parks`) use one word. The PN-R12 failure line changes the same word and the same fallback (D6): `Park names could not be read: <error>; Sandbox parks are shown by ID, first-played date unavailable.`

**D6. Hidden parks are named by the PN label helper. The server passes the labels to the page on each load, not through `data.js`.**
- The label `<name> (first played <Mon D>)` exists only in `park_label.labels` (`ingest/park_label.py:107-136`), which reads landing files, not marts (map TOP 5). `data.py` cannot read it (ADR 0054). A label read inside `_build` goes stale, because `_build` runs only when the warehouse changes (PN spec, PN-R12; map TOP 5).
- PN-R12 already reads the labels of the practice parks in the `_refresh_unfiled` path on each page load. This spec keeps that one read and its result: a mapping from Sandbox park ID to label, kept on the `Dashboard`. The banner sentences and the page's labels both come from it. The read is not done twice.
- **One fallback for both surfaces.** `dashboard_sandbox.py` holds one function that returns a park's label: the helper's label when it has one, else `<park ID> (first-played date unavailable)`. It applies when the read fails and when the helper has no label for that park. The banner sentences and the script both call it, so every Sandbox park has an entry in the script and the page never builds a label itself. The switch therefore never shows a bare name: it shows a dated label or the ID with the unavailable-date mark. Two same-named parks stay apart because their IDs differ.
- `Dashboard.page` adds, right after the banner `<div>`, `<script>window.DASHBOARD_LABELS = <JSON>;</script>`, but only when the current build has a Sandbox park. The JSON maps each Sandbox park ID to its label or, by the fallback above, to `<park ID> (first-played date unavailable)`. It is written with `json.dumps` (ASCII only), and every `<` is replaced by `\u003c`, so a park name cannot close the script element. Gain: the switch and the banner always name a park the same way, from the same fresh read and the same fallback. Cost: a second page global beside `window.DASHBOARD`; ADR 0054 says the app reads one data file, so the new ADR (R14) records this exception.

## 5. Hazards and edge cases

- **Totals change meaning on every page.** By default, the profit, revenue, costs, cash, guests, "Sample: N parks" and ride lists of "All parks" now cover company parks only. Every page says so through the switch note (R8). The sample line counts the parks in view and stays true. Pinned by R3 and R8.
- **Ride names flip.** With one company park, rides have no ` (park)` suffix by default and gain it when Sandbox parks are included (R6). Two same-named Sandbox parks give identical suffixes in the included view (Q1).
- **Null park names.** Shown as the park ID in `data.js` (R1). The switch line uses the label first, which already handles a missing name (`park_label.py:126-128`).
- **Money.** Sums stay in mart dollars, and no tenths are read (D2; invariant 3).
- **Two clocks.** The figures use the company date. "First played" in a label is wall-clock time in the Mac's local zone (`park_label.py:33-36`; PN spec PN-R2). The switch prints the label exactly as the helper returns it, so the words "first played" mark that clock. The switch never shows a company date for a hidden park.
- **Two same-named Sandbox parks** (the 2026-11-15 case). The banner and the switch tell them apart through the helper's time-of-play rule (`park_label.py:116-134`). The picker and the ride suffixes do not (Q1).
- **Only Sandbox parks in the warehouse.** The default view is empty, and the sentence says why (R11). The switch is still drawn, because `shell()` draws `#parkBox` before it checks for months (`shared.js:64-72`).
- **One company park and no Sandbox park.** Unchanged: no switch, no `with_sandbox` scope, and no per-park scopes.
- **Label read fails.** The figures are untouched. The banner and the switch both show `<park ID> (first-played date unavailable)` for each Sandbox park (D6), so identity stays and the missing date is stated.
- **An existing warehouse built before `park_number`.** The rebuild fails, the last good build stays, and the banner names the step that rebuilds the warehouse (R18).
- **A month placed by position.** Hiding Sandbox parks can make a year start late or skip a month; every Executive placement uses the company month (R16).
- **A hand-typed query.** `?park=with_sandbox` or any non-park value selects the all-parks view, as `?park=all` does; only `?sandbox=shown` includes Sandbox parks (R7).
- **`data.js` size and rebuild time.** The `with_sandbox` scope repeats the all-parks arrays for every park, so with Sandbox parks present `data.js` grows by about one more all-parks scope (ADR 0054 measured about 300 KB for two company years in total), and a rebuild runs one more scope's queries. No change without a Sandbox park.

- Analyses state their sample (parks, players) and say "observational" unless an experiment design backs a causal claim.
- The plugin compiles to ES5 and stays within its measured per-tick cost budget.

Branch limits:
- No new dependency and no new stored state (cookie, browser storage or file).

- The dashboard opens only its warehouse copy and the landing files it already reads (ADR 0054; PN-R12).
